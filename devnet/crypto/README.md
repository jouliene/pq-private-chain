# Local PoW devnet wallet

The devnet uses the APV2 single-wallet payment circuit registered at profile SHA-256 `af88a0ac0caa5f0aa27d38d687b6cc39495a0aa2659ed4a7e5e74653724cc1b1`. The devnet build overlays the mined-reward hash and the wallet client on the pinned APV2 executable. All verifier, proof packet, receipt and ordinary fee semantics remain as registered. The upstream source is DigitalGuards/qnero at `f04c91307837c0231668383bec76ba98d89d2652`, with the original Cargo.lock and rustc 1.93.0. The [build receipt](evidence/BUILD.json) pins the compiler, sources and author installation.

A clean disposable Qnero checkout and offline-populated Cargo cache are required. Set `lab` to a new directory with sufficient build space. The reusable Cargo target may be shared sequentially across builds. The output must be a new file. Build from the project root and approve the resulting binary hash before deployment.

```sh
rustup toolchain install 1.93.0 --profile minimal
git clone https://github.com/DigitalGuards/qnero.git "$lab/qnero"
git -C "$lab/qnero" checkout --detach f04c91307837c0231668383bec76ba98d89d2652
(cd "$lab/qnero" && rustup run 1.93.0 cargo fetch --locked)
python3 -IB devnet/crypto/build.py "$lab/qnero" "$lab/target" "$lab/native" > "$lab/BUILD.json"
native_sha=$(python3 -IB devnet/crypto/check_build.py "$lab/native" "$lab/BUILD.json")
python3 -IB devnet/crypto/check_wallet.py "$lab/native" "$native_sha" experiments/advancing-payments/evidence/public-registry --prove
```

The `hash` role accepts a length-framed `C` plus 72 public bytes (reward context32, canonical note-receiving pk32, u64le amount). It derives the note rho and randomness as Qnero Poseidon2 byte hashes of the respective ASCII domain `PQDEV1/reward/rho` or `PQDEV1/reward/r` followed directly by those 72 bytes. The public 104-byte reward record appends its canonical 32-byte note commitment. A reward exposes its recipient key, amount, note opening and issuance context. Its future spend still requires the wallet's authorization and nullifier secrets.

The wallet generates a random 32-byte seed, creates a mode-0600 `seed` under an owner-only directory and computes a public 1,601-byte address. Seed restore and viewing do not build a prover. A freshly created wallet receives zero genesis notes. The controlling client can restore by placing its private backup at the same relative name with the same permissions and supplying current public history. A complete snapshot contains the selected 132-byte anchor header, all ordered public commitment leaves, reward records, receipt records and known spent nullifiers. The wallet authenticates the funded root and checks coverage, reward commitments, receipt opening and local spentness. It trusts its selected synchronized node for the branch identity, spent set and complete history. A branch change replaces the entire view. An inconsistent funded root, reward opening or incomplete funded inventory invalidates the scanned view. The client assembles the full common history and public tree in memory. History input pages contain at most 192 KiB. The single local SCAN reply retains spent and unspent owned rows at 42 bytes each; the 8 MiB Python pipe limit supports at most 199,728 historical owned rows. Larger wallets require paged result output.

The wallet first chooses the smallest single unspent note covering amount plus the fee of three, padding its second input with a fresh zero-value dummy. If needed it chooses the smallest sufficient sum of two positive notes whose resulting change fits the circuit. The payment amount must be a positive 62-bit integer; a wallet whose total is sufficient but dispersed across more than two inputs may need consolidation. Every transfer encrypts a payee note and a change note, including a zero-value change note for exact funding. Amounts, selected totals, real-input count and history belong to the local wallet client. The network receives only the APV2 packet. The client labels its own change after restoration using an encrypted, seed-bound memo tied to the output commitment. Selected balances exclude already-spent notes and zero-value change. Pending submissions can conflict until one confirms. Nodes apply the admission and branch rules independently.

The standalone fixture uses synthetic public contexts and branch snapshots to test wallet behavior. The devnet's separate multi-node campaign exercises actual proof-of-work reward issuance, transport and admission. The two [measured payments](evidence/WALLET_CHECK.json) occupied 230,206 bytes each. Proving took 9.067 and 8.877 s wall (17.601 and 17.294 CPU-s); the public-only checks took 10.481 and 10.426 ms CPU. The sender paid exactly 47 from one 50-unit reward, leaving zero change. The restored recipient paid 39 from that single receipt, recovered 5 units of change, and lost the orphaned effects when the wallet rescanned the earlier branch. Every fixture secret stays in an isolated temporary private directory and never enters public evidence.
