# Local PoW devnet wallet

The devnet uses the APV2 single-wallet payment circuit registered at profile SHA-256 `af88a0ac0caa5f0aa27d38d687b6cc39495a0aa2659ed4a7e5e74653724cc1b1`. The devnet build overlays the mined-reward hash and the wallet client on the pinned APV2 executable. All verifier, proof packet, receipt and ordinary fee semantics remain as registered. The upstream source is DigitalGuards/qnero at `f04c91307837c0231668383bec76ba98d89d2652`, with the original Cargo.lock and rustc 1.93.0. The [build receipt](evidence/BUILD.json) pins the compiler, sources and author installation.

A clean disposable Qnero checkout and offline-populated Cargo cache are required. Set `lab` to a new directory with sufficient build space. The reusable Cargo target may be shared sequentially across builds. The output must be a new file. Build from the project root and approve the resulting binary hash before deployment.

```sh
rustup toolchain install 1.93.0 --profile minimal
git clone https://github.com/DigitalGuards/qnero.git "$lab/qnero"
git -C "$lab/qnero" checkout --detach f04c91307837c0231668383bec76ba98d89d2652
(cd "$lab/qnero" && rustup run 1.93.0 cargo fetch --locked)
python3 -IB devnet/crypto/build.py "$lab/qnero" "$lab/target" "$lab/native" > "$lab/BUILD.json"
native_sha=$(python3 -IB devnet/crypto/check_build.py "$lab/native" "$lab/BUILD.json")
python3 -IB devnet/crypto/check_wallet.py "$lab/native" "$native_sha" experiments/advancing-payments/evidence/public-registry --prove
```

The `hash` role accepts a length-framed `C` plus 72 public bytes (reward context32, canonical note-receiving pk32, u64le amount). It derives the note rho and randomness as Qnero Poseidon2 byte hashes of the respective ASCII domain `PQDEV1/reward/rho` or `PQDEV1/reward/r` followed directly by those 72 bytes. The public 104-byte reward record appends its canonical 32-byte note commitment. A reward exposes its recipient key, amount, note opening and issuance context. Its future spend still requires the wallet's authorization and nullifier secrets.

The wallet generates a random 32-byte seed, creates a mode-0600 `seed` under an owner-only directory and computes a public 1,601-byte address. Seed restore and viewing open only the wallet keys and receipt decoder. A freshly created wallet receives zero genesis notes. The controlling client can restore by placing its private backup at the same relative name with the same permissions and supplying current public history. The retained full-scan comparison mode takes the selected 132-byte anchor header, all ordered public commitment leaves, reward records, receipt records and known spent nullifiers. The wallet authenticates the funded root and checks coverage, reward commitments, receipt opening and local spentness. It trusts its selected synchronized node for the branch identity, spent set and complete history. In full-scan mode a branch change replaces the entire view. An inconsistent funded root, reward opening or incomplete funded inventory invalidates the scanned view. The client assembles the full common history and public tree in memory. History input pages contain at most 192 KiB. The single local SCAN reply retains spent and unspent owned rows at 42 bytes each; the 8 MiB Python pipe limit supports at most 199,728 historical owned rows. Larger wallets require paged result output.

The wallet first chooses the smallest single unspent note covering amount plus the fee of three, padding its second input with a fresh zero-value dummy. If needed it chooses the smallest sufficient sum of two positive notes whose resulting change fits the circuit. The payment amount must be a positive 62-bit integer; a wallet whose total is sufficient but dispersed across more than two inputs may need consolidation. Every transfer encrypts a payee note and a change note, including a zero-value change note for exact funding. Amounts, selected totals, real-input count and history belong to the local wallet client. The network receives only the APV2 packet. The client labels its own change after restoration using an encrypted, seed-bound memo tied to the output commitment. Selected balances exclude already-spent notes and zero-value change. Pending submissions can conflict until one confirms. Nodes apply the admission and branch rules independently.

The standalone fixture uses synthetic public contexts and branch snapshots to test wallet behavior. The devnet's separate multi-node campaign exercises actual proof-of-work reward issuance, transport and admission. The two [measured payments](evidence/WALLET_CHECK.json) occupied 230,206 bytes each. Proving took 9.067 and 8.877 s wall (17.601 and 17.294 CPU-s); the public-only checks took 10.481 and 10.426 ms CPU. The sender paid exactly 47 from one 50-unit reward, leaving zero change. The restored recipient paid 39 from that single receipt, recovered 5 units of change, and lost the orphaned effects when the wallet rescanned the earlier branch. Every fixture secret stays in an isolated temporary private directory and never enters public evidence.

## Incremental wallet

Ordinary balance, restore and send use `wallet_sync.py`. The selected history feed contains a bounded common sequence of public blocks, reward records, nullifiers and encrypted outputs. The validated local node authenticates the selected branch and provides its transaction identifiers and ciphertexts. The wallet checks contiguous parent IDs, retained AP-header ancestry, the block's seal binding, reward amount and commitment, public state transition and funded root. Owned decryption binds the note to its commitment. The compact feed omits block templates, PoW nonces and proof packets. Independent validation of PoW, packet verification and ciphertext coverage occurs at the full node. Each wallet's queries disclose cursor/locator timing to that node and contain only public branch identifiers and ranges.

A mode-0600 SQLite file under the wallet's private owner-only directory stores the cursor and header, accrued fees, positive balance totals, owned note source records and nullifiers, selected spending status, owned-related transaction IDs and current positive unspent membership paths. A reward source occupies 104 B. An encrypted output source occupies 1,824 B. Ownership, paths and matching nullifiers stay in the local wallet directory or its isolated processes. Deleting the eight-block undo horizon does not erase historical owned note records; SQLite can retain freed pages. The seed and common chain history recover confirmed state and spendability. Restoring a seed into a new directory does not carry pending intents, attempts or reservations; those belong to the separate sender outbox.

For `N` public commitments the right frontier holds 32 bytes times the sum of base-four digits of `N`. A positive unspent note stores three sibling digests per level, or `96 × depth` B, for depth 1–20 and capacity `4^20`. Each appended leaf hashes one path from the right edge. Each tracked positive unspent note changes one sibling at its highest differing base-four digit, with a new level on depth growth. The implementation loads and updates the wallet's live witnesses for each changed block. Its retained undo snapshots can cost up to eight previous sets of live path bytes, plus private SQLite row and index overhead. Selection can visit every positive unspent owned note. These costs depend on owned inventory and new commitments. The unchanged balance query reads one bounded locator and cached totals. The full-scan oracle's 8 MiB inventory reply limit applies only to its comparison interface.

Recovery commits a whole page of at most 16 blocks atomically with `synchronous=FULL`. A malformed continuation, later block or final endpoint cannot advance that page's cursor or inventory. Previously accepted pages survive an interruption. The stored frozen descriptor includes height, block ID, AP header, note count and anchor. A completed nonempty or resumed prefix captures one newer head and processes its suffix in the same call, subject to the operator's optional block limit. If mining advances again, the displayed height identifies the completed prefix. A branch change rewinds local notes, spentness, transaction associations and paths to a retained header; a missing common undo checkpoint triggers seed-backed replay from genesis. Up to eight successive branch changes per call are permitted. The next call resumes the last committed checkpoint.

The native `D` command checks one public reward or attempts one ciphertext with the incoming viewing key. The private `K` command re-opens each pinned positive input, checks its membership against the selected funded root, and builds the registered APV2 proof. It takes a header, amount, address and one or two owned source records with unsorted sibling triples. The sender preserves the same positive inputs across replacement proofs. A one-input spend uses a fresh dummy in the second slot. The public verifier and circuit registrations are unchanged. A real two-input compact proof on the archived H15 walkthrough took 8.852 s proving and 4.497 s setup. The 230,206-byte packet passed public verification and ordinary pool admission; a new recipient opened the expected amount. [Component proof record](evidence/COMPACT_PAYMENT.json)

The component fixture replays a completed walkthrough's real block files and the owner's test wallet in a disposable private tmpfs directory. The full-scan wallet and the incremental wallet agreed after shallow and deep reorganizations. Corrupted later roots and contradictory endpoint descriptors were rejected. This fixture calls the real chain interface in process. Operator campaign network counters measure the TCP application frames. In sync stats, `public_body_B` counts binary history bodies, including 9 B per nonempty page. `request_B` and `reply_B` include application framing and JSON metadata. `native_wallet` and `native_hash` separately count local framed role pipes. Their CPU deltas come from Linux scheduler ticks; `peak_rss_KiB` is the largest per-process lifetime high-water mark in each role's bubblewrap subtree. Controller CPU and lifetime peak RSS are separate. [State checks](evidence/SYNC_CHECK.json)

python3 -IB devnet/crypto/check_sync.py --home "$completed_walkthrough" --runtime "$lab" --wallet miner-a --prove

An installation with the previous published source receipt builds a verified new runtime under an installation lock. Completed generations reside together on the same filesystem. The installation first preserves a flat legacy pair as hard links, converts both top-level names into aliases for that pair, then atomically switches a single `active-runtime` symlink. Each directory rename is synchronized. Four simulated process interruptions between these publication steps left a matching old or new binary and receipt. The next prepare call completed publication using the verified generation. [Upgrade results](evidence/UPGRADE_CHECK.json)
