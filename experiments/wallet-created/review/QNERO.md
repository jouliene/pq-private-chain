A local run can show which paths the pinned wallet and runtime support. ## Wallet and verifier boundary

The release entity for a normal send is one zero-knowledge private batch with one real leaf and five padding slots. Each leaf has two input slots, permitting a dummy, and two actual output ciphertexts. A true 2x2 comparison therefore needs a funded input pair with neither note individually covering payment and fee. Count inputs inside each wallet, where the private distinction is available. Publishing the nonhiding leaf proof as evidence would reveal an intermediate the upstream design deliberately keeps local. A public aggregator can consume completed private batches. At default occupancy 53 independent one-payment wallets fill its 53 segments. The 318-slot combinatorial capacity assumes six real leaves in every segment and gives a different ownership/workload model. [Proof configuration](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/crates/qnero-circuit/src/config.rs) · [Aggregator](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/crates/qnero-aggregator/src/lib.rs)

Use the release profile's depth-20 quaternary membership tree (2^40 capacity), verifier artifacts and fixed dimensions. The README retains an earlier depth-16 description. The release private-batch public-input vector has 131 Goldilocks field elements including the common anchored header and six sets of nullifiers, commitments, fee and ciphertext digest. The release public-batch vector has 6,947 such elements, accounting for the aggregator identity and 53 inner segments. The verifier must check the selected artifact identity, proof, expected application public facts and both actual ciphertexts against the relevant digest. The circuit forwards the ciphertext digest as an unconstrained public value. The pallet binds it to actual bytes before admission. A public verifier also needs the anchor, current nullifier set, fee policy and exact atomic state transition. Sender-side verification alone cannot establish these or the recipient's ability to spend. [Release profile](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/docs/PROTOCOL-PROFILE.md) · [Runtime settlement](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/chain/pallets/shielded/src/lib.rs)

The native wallet’s `PreparedSpend` contains the public proof and ciphertexts alongside private change-note openings, selected input leaves and amounts. Export only the encoded public submission. A public-only verifier must run without those private fields or a hidden callback to the paying wallet. Record private outcome counts from the appropriate wallet seam without logging their values, debug dumps or the nonhiding leaf. The selected pinned hashes, not a sender-supplied verifier artifact, establish the expected circuit identity. [Wallet boundary](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/crates/qnero-wallet/src/wallet.rs)

## Role costs and limits

For the normal one-slot scale encoding, the overhead above the serialized proof is 3,600 bytes. It comprises the outer four-byte compact length, bare preamble, two call-index bytes, four-byte proof length, one-byte output count, two two-byte ciphertext lengths and two 1,792-byte ciphertexts. The 131 public inputs are already in the serialized proof. Occupied output slots remain visible. Reproduce actual counts using `python3 -I experiments/wallet-created/review/qnero_wire.py PATH_TO_PUBLIC_EXTRINSIC`. Its parser reads the wire and public proof suffix. Cryptographic acceptance is a separate test against the pinned upstream verifier. Distinguish JSON-RPC hex expansion, complete unsigned extrinsic size, pool/peer messages and retained block bytes when pricing one submission. [Wallet encoder](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/crates/qnero-wallet/src/extrinsic.rs)

A separate parser on the first actual public submission counted 150,908 proof bytes, 3,584 ciphertext bytes and 16 framing bytes. One of six slots held the ordinary payment; the funded wallet used one input and a dummy. The total was 154,508 bytes before peer overhead. The HTTP client's JSON-RPC request body was 309,091 bytes. At 100M included payments, direct submissions alone occupy 15.4508 decimal TB/year. For recovery of a full year in 90 days, the archive must serve at least 15.4508 TB of binary history and the client requires 15.896 Mb/s of history alone, before live operation, headers, trie proofs and other traffic. Stock JSON-RPC returns full SCALE bodies as hex strings, so the payment hex digits alone would occupy 30.9016 TB for the same one-year history. A different question, downloading only 90 days of payment history, gives 3.809786 TB binary or 7.619573 TB hex. These projections exceed the stock chain's capacity below. The retained binary and experiment are available in the [comparator evidence](../qnero/evidence/public/payment.scale).

The pinned wallet authenticates all historical block extrinsics against their header root, scans output ciphertexts, reads trie proofs for exact tree indexes and authenticates the complete spent-nullifier set. It trusts the configured node for chain selection and availability above the checkpoint, without checking cumulative RandomX work. A byte model charging only two ciphertexts per payment for recovery describes a proposed separately authenticated history lane. Stock cold recovery must also download proof-bearing block bodies and other data. An authentic commitment is of no use to an offline recipient if nobody serves the ciphertext-bearing body. An archive storing only the compressed post-inclusion chain does not retain independently re-verifiable inner mempool proofs. [Authenticated wallet reads](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/docs/AUTHENTICATED_READS.md)

There is also a hard stock wallet limitation at this workload. Each real settled slot inserts two distinct nullifiers, including the domain-separated dummy for a one-input payment. Wallet sync traverses the entire UsedNullifiers prefix. The proof reader caps that traversal at 1,000,000 entries, independently of paging, alongside 64 MiB and 1,000,000-node proof limits. Starting from an empty set with no other transactions, 500,000 accepted payments occupy exactly the entry cap. At a uniform 100M accepted per year, that is 1.825 days. Byte/node limits may intervene sooner. No year-long stock-wallet recovery claim follows from a short successful payment or a hypothetical compact history design. [Wallet prefix read](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/crates/qnero-wallet/src/chain.rs) · [Prefix verifier limits](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/crates/qnero-state-proof/src/lib.rs)

The native runtime uses a 120-second target, 5 MiB maximum blocks and a 75% normal-dispatch share, amounting to 3,932,160 normal extrinsic bytes per target interval before unrelated transactions. At 100M accepted in 365 days, the mean demand is about 381 ordinary payments per target interval. At one private proof per roughly 150 kB payment, the direct path exceeds native single-chain block capacity even before weights. Live or archive comparisons using a different cadence/limit are legitimate designs of the independent protocol and should be named accordingly. The stock pallet budgets repeated proof parse/verification during pre-dispatch and dispatch in addition to any pool admission. ## Assurance, tokens and atomic exchange

Spending authority and nullifiers use in-circuit hash relations. The notes/tree use Poseidon2, while proof Merkle commitments and Fiat–Shamir use original Poseidon. The pinned profile uses a quadratic Goldilocks extension, 28 queries, log inverse rate three, two challenges and 16 grinding bits. Upstream separately records an approximately 95-bit cryptanalytic caveat for the original Poseidon parameters. The 100-bit conjectured FRI target and this caveat give no uniform classical or quantum level for the complete suite. ML-KEM-1024 followed by ChaCha20-Poly1305 protects honest note contents under its own assumptions. Recipient anonymity under chosen-ciphertext/adaptive, multi-user and later viewing-key-compromise models remains a separate claim. Exact suite ciphertext lengths hide memo-length differences but public fees, submission layout, anchors and network timing remain observable. Comparing source proofs, finite timing and negative controls cannot prove whole-protocol hiding. [Pinned cryptography inventory](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/docs/CRYPTOGRAPHY.md)

The ordinary circuit conserves a single bounded scalar denomination. Adding a public label to the envelope does not create a multiasset relation. A candidate token transfer must tie the same asset identifier to each committed note/authorized opening and independently enforce nonnegative bounded conservation in every distinct asset. Only the native asset funds the native fee. A token-only input, unauthorized mint, changed token identifier, or reuse of one native-funding input across two legs must fail. The chosen disclosure of asset identifiers and native fee activity, issuance/burn authority and anchor/version binding change the application semantics. These are obligations on both constructions if token support is claimed.

Native public aggregation deliberately permits selective segment settlement when a segment's anchored block is stale or a nullifier already spent. The other participants' valid segments can still settle. A two-wallet aggregate can certify two private payments while permitting one-sided exchange. A swap requires both owners to authorize the same bound two-leg order, with reciprocal assets, values, recipients, common context and expiry/cancellation semantics; each wallet also needs assurance that its promised ciphertext opens to a spendable note. Bind fresh authorization to this joint settlement mode to prevent applying either ordinary leg separately. Validate both inputs, receipts, change, native fee and resulting state before atomically accepting either side. Cross-participant conflicts, replay and rollback should preserve all-or-nothing settlement. A useful negative test makes one authorization stale while the other remains valid and then presents the original legs separately. This is a proposed test and relation change, and no native Qnero swap result is claimed here.
