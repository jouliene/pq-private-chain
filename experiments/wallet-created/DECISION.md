# Wallet-created payment validation

**Defer network integration of both candidates.** Keep CP03 as the executable reference and retain the complete WHIR wallet backend for comparative research. WHIR speeds up the earlier sparse WHIR verifier, cuts complete payment size versus CP03 and preserves the CP03 payment semantics, but the executed parameters have no quantified noninteractive post-quantum authorization/privacy claim and the required public history remains costly. The native pair demonstrates real archival savings across independent owners, but introduces a different nullifier/tree and weaker assurance profile, high builder work and an unresolved funding-anchor/state path. Both 1 and 5 TB are comparison scenarios; the owner has set no archive or annual traffic ceiling.

The first full masked-WHIR wallet payment and the two-owner native experiment answer different participation questions. The former preserves the working CP03 ordinary-payment relation while changing its proof. The latter tests whether separate wallets can submit privately proved authorizations to a builder and retain only one recursive proof in the block. The comparison baseline is public revision `a131ee5881e89e02f721fcfc3b5d01225437366e`. The original CP03 implementation remains executable and unchanged. Global blockchain development remains **ACTIVE**.

## What a complete WHIR payment established

The full body comprises a versioned 20-byte header, 528-byte authoritative public statement, two 2,164-byte ML-KEM-1024/HKDF-SHA384/AES-256-GCM envelopes and a salted masked-sumcheck/WHIR proof. The fixed program checks ownership, both occurrence-bound nullifiers, both ordered depth-40 memberships and index bounds, output commitments, bounded integer value conservation and the fee. The verifier derives its program and public projection locally. It absorbs the entire canonical statement, including the receiving-context digests. The node independently associates each actual envelope, slot and commitment, checks funding/branch context and spentness and applies the effects. The receipt binds what was sent; recipient opening is a separate wallet operation. ## What must be assumed

The four precommitted independent base-field blinds make the four subfield replies jointly uniform at fixed independent base challenges. Subsequent outer messages and terminal openings interrogate the *same* commitment. The argument conditions the source encoding on the four replies and witness, then relies on independent outer masks, bounded RS query simulation, code switching and independently blinded terminals. The extra challenge/reply round must preserve the per-round knowledge/extraction conditions of the compiler. The hashes of roots and direct messages determine challenges; deterministic Merkle evidence is checked against committed roots. This is a source-mapped interactive argument with explicit remaining composition work. [Transcript, terminal and extraction analysis](structured/ASSURANCE.md) · [CFW](https://eprint.iacr.org/2026/391)

The selected schedule's estimated interactive error is about 2^-130.49. Even a valid application of the generic CMS quantum random-oracle theorem has a term proportional to t² times that error for t quantum oracle queries, as well as the hash-collision and verifier-query terms. This particular sufficient bound loses force around 2^65 queries before constants; it supplies neither an attack of that cost nor a 128-bit post-quantum work factor. The exact SHA3-512/SHAKE256 transcript, private randomness expansion, multi-user adaptive statement selection and circuit/receipt composition need qualification. ML-KEM ciphertext confidentiality, recipient anonymity, note unlinkability, network sender anonymity and recipient safety under later key compromise are distinct properties. [CMS theorem and compiler qualifications](https://eprint.iacr.org/2019/834) · [receiving and ledger obligations](../../docs/network-feasibility/OBLIGATIONS.md)

## What the stock Qnero comparison established

At upstream commit `f04c91307837c0231668383bec76ba98d89d2652` the ordinary wallet spent one funded input plus a zero-valued dummy, used one of six private batch slots and sent a full standalone 154,508 B extrinsic. The 150,908 B proof already contains all 131 public field elements. The two ML-KEM-1024/ChaCha20-Poly1305 ciphertexts cost 3,584 B together and the extrinsic's SCALE framing costs 16 B. The wallet's JSON-RPC submission body was 309,091 B; preparation and funding sync generated additional requests. The stock nonhiding leaf stayed inside the wallet. A separate wallet and a fresh seed restoration recognized the payment from authenticated public fixture history. A newly funded real proof also passed pool validation, pre-dispatch and dispatch in the unchanged pinned FRAME pallet using an explicitly installed laboratory anchor. A replay failed all three paths. No public mining, online submission or public peer capture is used as evidence. [Byte accounting and executable commands](qnero/README.md) · [independent comparator](review/QNERO.md)

A separate metered default-wallet run forced **both input notes to be real**. It still emitted a 154,508 B ordinary transaction. The single submit request comprised 17 B request line, 119 B headers and 309,091 B JSON, totaling **309,227 B outbound HTTP**. The sender spent 3,056 B of outgoing HTTP preparing, 311,579 B submitting plus confirming, and 4,261 B syncing initial funding, for **318,896 B** for these sender phases. The recipient and backup-only restoration each sent another 5,770 B. The full 62-request exercise sent **330,436 B** at the application layer. Each unknown full peer contacted by the pinned transactions protocol gets a 154,509 B notification including its SCALE vector prefix. The encoded laboratory block occupied **154,680 B** including a 171 B header and the extrinsic vector. TCP/IP, TLS, real block authors' other extrinsics and live peer fanout are separate. [HTTP and exact packet fixtures](qnero/http/README.md)

Qnero's fixed proof profile has a conjectured 100-bit target, 28 FRI queries at rate 1/8, 16 grinding bits and degree-two extension challenges. Its proof hash is original Poseidon; the note constructions use Poseidon2. The release tree is depth 20 with four sorted children, or capacity 2^40. CP03's depth-40 binary tree privately authenticates an ordered funded occurrence. These variants have different replay/duplicate-note semantics. The six-slot stock proof publishes twelve distinct nullifiers. Only the two in the active slot enter spentness, including one dummy-input nullifier in the single-funded-input send. The wallet reconstructs its membership tree from all public leaves at spend time, and its full spentness-prefix scan has a one-million-entry cap. That count alone is exceeded above 500,000 default payments; proof-node/byte caps can bind earlier. At the pinned 120-second target and normal class allocation, at most 25 such standalone extrinsics fit before other transactions, about 6.57M/year. Scaling to 100M accepted payments/year requires changing the stock design. [Pinned-source and cost analysis](qnero/ROLES.md)

## Two actual senders and one retained proof

Two separate wallet processes received four independent funded commitments as public genesis and exchanged only their public addresses. Each originated its own 2-in/2-out payment, including a payment to the other party and change. The builder received **two 147,324 B wallet packets**, comprising one 143,732 B hiding proof, two 1,792 B ciphertexts and 8 B framing each. The pair retained **157,220 B** including one new 150,044 B recursive proof, four unchanged ciphertexts and 8 B framing. This saves **137,428 B** out of 294,648 B of submitted bodies for this pair. Pre-inclusion uploads cost the full 294,648 B; a builder that received the inputs can still recognize their public effects in the pair. Only two actual payers earn amortization. The binary test pipes charged four additional bytes per frame; the raw record includes every frame in both directions, including genesis/addresses, receipt diagnostics and the subsequent payment. [Independent wire decoder](review/native_wire.py) · [inputs and measured byte accounting](native/evidence/WIRE.json)

Both wallets opened their two expected receipts. One spent those proceeds in a new 147,324 B proof-carrying payment accepted under the next anchor. The node rejected a modified proof, a canonical fee change, a ciphertext mutation, truncation, trailing data and replay without publishing new state. The verifier for the pair and the verifier for the successor are independently derived from fixed source, with 1,741 B and 1,769 B of serialized verifier data respectively. The builder spent 16.82 CPU seconds (8.64 seconds elapsed) verifying and wrapping the two public submissions, peaking at 1,071,008 KiB. The wallets used 8.79 and 9.40 CPU seconds for their payments after setup and peaked around 548 MiB. The node accepted the pair in 10.85 ms CPU on the four-leaf fixture after 9.91 CPU seconds of circuit preparation. This last measurement includes the small-state transition; the in-memory fixture has no durable network DB. ## Independent operation

The researcher profile is four physical cores of which two core-seconds/s are reserved for validation, 16 GiB RAM, 4 TiB usable disk, 80/16 Mb/s useful down/up, six inventory peers and one requesting full-payload peer. The owner supplied the 100M offers/year workload. Admission fraction, fanout, burst (10× for 600 seconds), 90-day catch-up and the 1/5 TB archive scenarios are inputs to the following estimates. Ledger headers, peer control and replication costs are charged explicitly in the [role model](ROLES.md).

- **Wallet and archive.** At 100% inclusion, WHIR uploads sum to 26.3292 TB, and one canonical archive with the modeled framing grows by 26.336 TB/year. The native experiment uploads 14.7324 TB of independent wallet submissions before inclusion and retains 7.861 TB/year of pair packets before outer chain framing. Keeping all successful native inner packets as well would require another 14.7324 TB. A complete copy of direct stock Qnero extrinsics would grow by 15.4508 TB before shared block data; its present runtime cannot include that volume. At 100M inclusions the 1/5 TB comparison points allow only 10,000/50,000 bytes per payment before other obligations. None of the measured formats meets either comparison at that occupancy.
- **Live and burst.** WHIR's projected single-requester upload is 6.68 Mb/s for block-only and 13.37 Mb/s for mempool plus blocks. Both fit a 16 Mb/s steady link; the 10× queue takes about 55 minutes to drain for block-only and about 7.5 hours for both phases. Native pairs reduce post-inclusion relay while retaining full wallet submissions and builder intake. Even with only valid offers and perfect pairing, a complete native builder processing the full offered stream would consume about 26.7 core-seconds/s for wrapping alone on the measured CPU. This work may be distributed among builders only under an actual compatible inclusion/anchor policy.
- **Pruned disk and catch-up.** The inherited engineering model puts a WHIR node with a 256-block retention window at about 0.875 TB after one fully included year. An archival service must still make the discarded bytes available. With a prepared verifier and the small-database ledger rate, the projected one-year historical plus live WHIR workload can fit the two validation cores under the 90-day scenario. Starting a verifier for each payment cannot sustain even the mean stream, and preparing per three misses this catch-up target. The loop does not measure a mature database, forks, peer service or sustained 90-day processing. The native fixture rehashes the entire ordered commitment list each time it derives an anchor. With two new commitments per sender, the current code feeds an accumulated 160 PB of commitment bytes to that hash across 50M pairs, before per-pair domain/count framing, tree work and indexes. This is cumulative computation, not retained disk.
- **Cold wallets and source availability.** A CP03-compatible common history would carry about 502.24 GB/year for receipts, occurrence witnesses and cursor updates at full inclusion. It assumes an available validating history source, the saved key inventory and compatible branch service. The full WHIR evidence here uses approved public bodies and short histories. Stock Qnero cold recovery reads full block bodies and spentness proofs and hits the documented default cap. The native prototype delivers 7,296 B of compact public history for the two payments after validation. A verified recovery service, persisted key/seed recovery and a year of eligible-branch history do not follow from that small response. A cold independently validating node must source full public bodies/blocks or another independently demonstrated method. [Disaggregated traffic, state, CPU and service projections](ROLES.md) · [stock recovery limits](qnero/ROLES.md)

Both experimental ledgers require the current anchor. Neither sampled throughput represents a live permissionless network where many independent wallets can prepare in parallel and their transactions still settle after another accepted block. The existing CP03 research ledger has a retained eligible-anchor policy; mapping new verifier identities and nullifiers into that policy, preserving current-branch conflict checks and reorg behavior, is still an integration step. A replay of previously created dependent payments and matrix reuse across 96 statements do not establish independent origin capacity.

## Decision-changing evidence

For WHIR, an independently reviewed round-by-round extractor/joint simulator and a quantitative compiled security bound for the **actual** challenges, salts, base-field guard and multi-transaction setting could change the security decision. Larger schedules need fresh end-to-end byte and cost measurements. For example, even holding the first-list size fixed at 11,088, the four-guard bound gives about 169.85 bits, while **six** would give about 261.50 bits for that component alone, using the source bound `L × (296448/p)^k`. Raising only this count does not improve all other interactive error terms or justify a complete quantum claim.

For native aggregation, two independent wallets demonstrated the mechanism; a 53- or 318-payment amortization has no experimental basis here. The next discriminating experiment is one blinded, **four-independent-wallet** batch under a registered, quantitatively justified security profile, with an eligible retained anchor, current spentness checks and an incremental authenticated state update. Measure all four wallet submissions and one received/verified complete block packet, including eight ciphertexts and the full effects needed for recovery. Under the illustrative 5 TB scenario a four-payment group has a total 200,000 B allowance before shared block overhead. Report actual intake, builder CPU and availability of history even if the block fits. Freeze the security profile and its assumptions before treating the byte result as grounds for integration. This is a proposed next experiment, beyond the tested pair. The concrete token/native-fee and two-owner all-or-nothing swap designs are specified separately and remain unimplemented.
