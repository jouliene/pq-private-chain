# Independent live TKN1 acceptance

Baseline `b5fe043`. The non-author will build the frozen implementation in a detached clean checkout, generate new disposable wallets and run the ordinary published wallet/node commands. The prior isolated TKN1 fixture used four sealed transfers, a native fee sink and a supplied genesis. Its transactions do not establish behavior of a live fee-paying reward, real peer selection, wallet outbox, cold peer or orphan recovery.

| Question | Observation required |
|---|---|
| What did the peers actually select? | Capture all distinct full public blocks for both tips, visit their parents back to approved genesis, recompute the winning work and deterministic tie rule, check the direct parent seal in each template, then independently rebuild each complete branch. A fresh peer with only genesis and its approved executable must receive and verify public blocks and reach the same funded root, work, spent-set hash, native/token issuance and fee count. A before/after empty cold record and peer fetch observations distinguish this from reopening a copied DB. |
| Who received each fee? | For every selected and detached block sum the fees of its verified slot statements. Compute reward amount from the local subsidy rule plus exactly this block's fees. Recompute its typed commitment from the frozen public miner, parent, height and payment context; require zero token reward, native subsidy accounting and every output/reward in the published tree order. Check nonempty competing branches with distinct fee totals, partial shared history, and zero residual detached reward/fee credit in the selected wallet/state. Report both per-block and branch totals. |
| Can a wallet spend a paid mining reward? | With a controlled miner whose only qualifying funding is the identified reward, observe the ordinary wallet's resulting payment, selected inclusion and denomination. A wallet-held inventory before/after may disclose synthetic counts and values. An opaque nullifier alone proves neither the input position nor real-world owner. If testing detached reward spending, require original acceptance on the losing branch and zero effect on the replacement branch; cold wallet zero balance or an unavailable input must not be conflated with a checked proof. |
| What was duplicated or renewed? | Independently verify each distinct public packet from network exposure, SHA-256, public input words and ordered receipt digests. Identical retransmission has identical bytes. A newly created stale replacement has different bytes and a shared real nullifier with its predecessor. Confirm stale/eligible anchor against current tips, the exact duplicate response on a receiving peer, conflicting pool or selected status if exercised, at most one selected economic effect/fee for the named intent, and every attempted packet's placement or absence across reorg. Distinguish deliberately repeated transport bytes from re-proving. |
| What does the live user recover? | Record the initial synthetic holdings, offline address import, externally paid receipts, seed-only rescan against authenticated history, new spend, returned change in both lanes and final balances. Compare against full public totals plus the recipient-side measured opening. Disclose which labels/values were deliberately recorded by the fixture. Keep addresses' private counterparts, opened note randomness, paths, seeds, private outbox and private node home outside release evidence. |
| Which parameters and claims changed? | Inspect the source, regenerate and compare the approved verifier and report actual parameters of any stronger profile and whether it ran on a comparable full payment. Distinguish tested verifier incompatibility from estimated work factors. Report proof/wire bytes, CPU including/excluding setup, native high-water RSS, stake of metadata, limits of the finite PoW history and unfinished formal privacy/soundness or service claims. |

The portable public inputs should contain a trusted genesis hash and complete founding record, canonical raw block objects keyed by ID, exact nonselected retry packets, and selected/orphan snapshots or named tips with proof/relay request observations. At least two distinct private economic authorizations may have equal nullifiers. Any identifying conclusion about a particular business intent uses independently described lab provenance. Authorization is checked with the validator's registered native key in a process with no wallet mount. Tree and receipt arithmetic will use unmodified, separately linked upstream primitives; the review oracle will not import the implementation's ledger acceptance or fork choice. Any exception will be recorded in the result.
