# Ordinary profile-C transfer and its selected-ledger effects

The statement here concerns the native and token face values carried by committed notes in an ordinary MSP3 transfer at candidate height 25 or later. The node learns a fee of 3 and a zero supply descriptor. The transfer's token ID and quantities are private. Conserving a given witness, attributing its inputs to unique previously funded notes, and deriving such a witness from acceptance of arbitrary proof bytes require different premises.

For ordinary transfers put `M = 2^62 − 1` and `p = 2^64 − 2^32 + 1`. Each native input sum is at most `2M`, and each sum of native outputs plus fee is at most `2M + 3 = 2^63 + 1 < p`. The token input and output sums are each at most `2M = 2^63 − 2 < p`. In both equations, equality of canonical residues implies integer equality. There is no integer-overflow step in the ledger's Python fee computation. Base-field arithmetic still applies to digest gadgets, selectors and other relations; this lift covers the monetary sums.

## Ledger update and cryptographic boundary

| State step | Staged source and accounting |
|---|---|
| Eligibility and spentness | `devnet/swap_ledger.py:85–93` dispatches a singleton to `devnet/chain.py:313–331`. Every admitted ordinary payment checks freshness of both NFs, distinctness of both effects per type, and no previous output CM. `chain.py:356–365,370–372` also excludes duplicates across all current slots and the reward CM. The state records NFs for both real and dummy slots. Accepted-value accounting attributes real NFs to exactly the corresponding old openings; cross-domain hashing alone gives no mathematical proof that their output images never intersect. |
| Registry | `devnet/managed_ledger.py:61–64`, `devnet/chain.py:412–417`. A zero delta skips the issuance check and no registry event is inserted. A C proof for a distinct issuance/burn operation has different ledger effects; pairing an issuance proof with the ordinary envelope fails the operation check. An accepted nonzero hidden token ID's historical legitimacy depends on correct prior issuance and input-opening membership. |
| Fee, reward and supply | `devnet/chain.py:21–30,356–381`. On an ordinary-only block with k singleton payments and 0 ≤ k ≤ 4, slots pay 3k, the unique reward note receives 100 + 3k native and 0 tokens, and the separately tracked issued amount is h × 100. Thus committed native face value increases by exactly 100 and every token total remains unchanged. The cumulative `fees` field is a counter, never an extra spendable credit. Python checks reward < 2^62 and cumulative fees + h × 100 < 2^63. The node constructs reward CM using the separately approved hash role on context, miner pk, reward and zero token, requires a nonzero fresh CM and includes it once. `devnet/runtime.py:20–25`, `experiments/advancing-payments/run.py:73–86` select that hash role. The shared reward constructor appears in `wallet.rs:30–57` and the common hash-command generator in `experiments/payment-architecture/direct/build.py:42`. A single ordinary payment contributes 3 to the one block reward; a single-payment block has reward 103. |
| Atomicity, branches and genesis | `devnet/chain.py:127–156,210–218,395–420,456–505`. Genesis has no live outputs or premine. A selected block is re-derived, including its reward and state header, before effect rows are inserted. The same SQLite write transaction inserts its selected height, two NFs and two output rows per singleton, any authorized asset events, and one reward. On failure it rolls back; on a losing side branch a savepoint restores selected state while retaining independently checked side-block data. A winning fork deletes the detached-height effects and replays the preferred branch. The theorem concerns the currently selected logical branch. Mempool reservations, archive copies, detached output rows, cumulative counters and volatile observations contribute no additional live money. |

Integer conservation holds for a satisfying witness even if a recipient fails to open a ciphertext. Lifting it to the selected ledger requires proof validity to imply the pertinent witness statement; identifying funded openings and preventing cross-note/cross-domain NF aliasing requires the cryptographic binding and representation premises. A concretely known counterexample to one of those premises would invalidate that lift. This correspondence does not provide Plonky2 knowledge soundness, a quantum hash bound, note-owner privacy, recipient spendability, or verification of earlier A/B, supply-management or swap transitions. An opening-level starting inventory supplied by those earlier transitions remains a premise of an ordinary C suffix theorem.

## Interface to the machine-checked statement

The declarations in [Conservation.lean](Conservation.lean) split the following obligations.

| Lean fields | How the premise is obtained |
|---|---|
| `Gates.ri/rj/ru/rv`, `nativeEq/tokenEq`, the four `Tag` fields, `zeroAsset`, `iDummyGate/jDummyGate` | Interpret the above range checks, arithmetic connects, typed-opening hash preimages and selector checks on a satisfying MNG3 ordinary witness. Converting a malicious proof acceptance to that witness/statement is an external proof-system premise. |
| `SlotLink.realMember/realKey` | Membership at the eligible anchored *prefix* gives an occurrence in the selected history under the header, Merkle and note-binding assumptions. The node retains selected output CMs even after consumption. Funding ownership, true NF and exact asset opening of that occurrence must agree with the witness. A fresh published NF combined with this correspondence excludes already-spent real inputs. |
| `SlotLink.dummySeparate`, `Admission.selectedUnique/freshIds/uUnspent/vUnspent` | These compare private true NFs of funded or newly created openings. The ledger cannot query them. Real/dummy domain separation and output rho derived from two NFs plus the index support the assumptions. They do not establish unconditional non-aliasing. A new output may even have an arbitrary publicly unopenable spend key; a faithful opened-inventory model still requires a consistent assigned true identity. |
| `Admission.inputKeys/iUnseen/jUnseen/distinctOutputs/freshCommitments` | Lean derives the existence of a real input from ordinary fee arithmetic and the dummy gates; the circuit also has an explicit nonpadding gate. The circuit/native codec and the selected state's SQL checks enforce the public distinctness/freshness facts listed above. Block-wide cross-slot CM and NF uniqueness also matters when composing several payments. The released devnet node checks each singleton against the same eligible pre-block anchor; sequential model steps represent the net effects of those already validated independent slots. |
| `State.funded/spent`, `settle`, `ordinary_block` | The two selected `outs` inserts, two `spent` inserts and single reward insert model append-only history for that branch. Lean lists place newly created notes at the front; SQL appends them in position order. The holdings sum and membership projection ignore order. The protocol hashes *actual append order* for its root. The reward's ordinary amount, zero token, freshness of public CM and unique insertion are checked by the node. Its hidden true NF being unspent remains a separate opening premise. |
