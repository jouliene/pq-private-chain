# Distributed custody control

Register a materially different fallback to expensive delayed recursion. Use the complete earlier DLF1 validation objects, including every public wallet proof, receipt, miner reward, commitment and nonce. Each accepted block is split into four equal padded data slices and two Reed–Solomon-style parity slices over GF(256). Pin the code, network and profile. Use six separately addressable storage directories. Store one common, ordered, hash-authenticated shard manifest with each holder. Recover in another process from the independently specified selected tip and four holders, with two data holders unavailable, and execute the ordinary native DLF1 verifier and state transition from genesis. Test all 15 four-holder sets, corrupt data, and loss beyond tolerance. Record actual files, recovery I/O, coding work, native checks, sparse/busy projections, and total encoded vs independently complete archival storage.

This is an availability and CPU tradeoff. A single custodian cannot cold-validate from its partial copy. An authenticated raw-block target and available remote fragments are necessary. There is no trusted validity signature, new succinct validity proof or permanent reduction in the data needed for full verification. No new wallet proving or mining is needed. Use the four-wallet public busy history from the released DLF1 path or a freshly independently generated history of the same interface. The original consensus binds each full block and proof. New partial-storage layout is external to that consensus.
