# Profile-C token supply changes

An accepted supply event changes two representations of a token on the selected branch. A complete MNG3 note proof changes the committed quantity, while the MSP3 envelope and node policy authorize and record the same signed quantity in the public asset registry. This correspondence covers the four supply opcodes. It uses the monetary field, ownership and funded-membership interface already examined for ordinary C payments. [Ordinary relation and checked sources](../funded-conservation/MAPPING.md)

## Rules on the public wire

Let `B = 2^62`, `MAX = B−1` and `q` be a positive magnitude, at most MAX. Each operation consumes a normal funded fee of 3 native units. A supply event exposes its effective asset ID and delta.

| Opcode | Wire and proof | Preconditions in the selected registry | Selected effect |
|---|---|---|---|
| 1, fixed issue | Unsigned MSP3; positive delta `q`. Fixed ID derives from the network and real first NF. | ID absent; sequence and previous event decode to zero. | Create fixed row with outstanding `q`, revision 1 and empty authority. No subsequent protocol mint or burn. |
| 2, managed registration | Signed MSP3; positive delta `q`. Managed ID derives from network, signing public key and real first NF. | ID absent; signature under supplied key valid; previous revision and event both zero. | Create managed row with outstanding `q`, revision 1 and immutable authority. |
| 3, managed mint | Signed MSP3; positive delta `q`. Its public ID must agree with the note proof. | Existing managed row, correct registered signer, signed previous revision and tx equal its current head, old outstanding + `q ≤ MAX`. | Increase outstanding by `q`; increment revision, keeping mode and authority. |
| 4, managed holder burn | Unsigned MSP3; delta encoded `B+q`. The holder proves funded inputs of that ID, sufficient for the burn and retained outputs. | Existing **managed** row with outstanding ≥ `q`. No issuer approval, referenced return transaction or signed prior revision appears on the wire. | Decrease outstanding by `q`; increment revision and retain mode and authority, including when outstanding reaches zero. |

Opcode 0 is an ordinary transfer. Its zero delta cannot be relabelled as any supply opcode. A fixed holder can transfer their tokens; the registry rejects a protocol burn of a fixed asset even if all the necessary notes are owned. A managed issuer cannot confiscate someone else's funded inputs. The issuer and the owner supplying the native fee may cooperate: the proof requires a real first input on positive issuance and the signature covers that inner packet, but the relation has no equality between the issuer signing key and the first note's private spending authority. The exact fee may be covered across both inputs.

In the materialized release, `devnet/managed_ops_c.py:6–13,21–40,66–79` specifies the envelope and operations. `devnet/managed_ledger.py:36–54,57–87` joins verified public effects to the opcode, authority, outstanding count and selected history. The original fixed ID algorithm is `devnet/asset_ledger.py:10–12`. Managed IDs preserve the `MNG1/managed-id/v1\0` domain across the C upgrade; the effective function imported by the ledger comes through `managed_ops.py` and `managed_ops_ab.py` from `managed_ops_a.py`. Both original ID algorithms take SHA-256 and clear the high bit of each little-endian 64-bit limb. A supply proof also requires the resulting 4-limb ID to be nonzero. The maximum field-sum intermediate before using the issuance guard is `3·MAX = 13,835,058,055,282,163,709`. This is below the Goldilocks modulus `18,446,744,069,414,584,321` by `4,611,686,014,132,420,612`. Input/output subtotals are at most `2·MAX`. Both the native and token sums therefore lift to exact natural-number equalities. Positive issuance gives `I=0, O=q`; burn gives `I=O+q`. For a different token ID, both sides contribute zero. Every input capable of supplying a positive burned quantity is real because dummy-token quantities are zero. These arithmetic conclusions concern satisfying witness openings, independently of fee-payer identity and recoverability of the ciphertexts.

## Signatures, event identity and rollback

The signed envelope fields are a 32-byte public key, an eight-byte little-endian previous sequence, a 32-byte previous transaction ID, a 17,088-byte signature and the complete inner MNG3 packet. Register and mint authorize the SHA-256 digest of the concatenation below. The network is the node's registered 32-byte domain. The opcode is one byte; `SHA256(inner)` covers the proof, its public inputs and both ciphertexts.

```text
MNG3/supply-auth/v1\0 || network || opcode || public_key ||
u64le(previous_sequence) || previous_tx || SHA256(inner)
```

The transaction ID used for the **next** predecessor is SHA-256 of this entire outer MSP3 packet, including the signature for signed events. The stored revision starts at one. A burn's unsigned envelope supplies no predecessor and the parser sets its auxiliary fields to zero. The node computes its new revision from the selected old row. Thus a burn invalidates a previously signed mint for the old head. Burning to zero neither unregisters nor exhausts mint authority: the same ID cannot be registered again, and a valid new signature under its original authority can mint from the latest zero-supply row. The cap is on **current outstanding** quantity and on one operation. Lifetime gross issuance can exceed it after burns. There is no global cap summed across asset IDs.

Generated `main.rs:96–110` verifies MNG3 for the inner command and uses a separate `V` command for the issuer signature. The ledger calls the latter only for signed operations, after checking the decoded proof. Generated `crates/qnero-notes/src/encrypt.rs:212–238` verifies the 32-byte authorization digest with that key and signature. The concrete upstream wrapper selects SLH-DSA-SHAKE-128f. The standard wallet derives this role's signing key from its own seed using the retained issuer-key domain. Consensus checks a valid signature by the enrolled authority, irrespective of that authority's key generation procedure. Neither signature verification nor ID hashing is an arithmetic MNG3 gate. [Signature implementation](../managed-assets/native/issuer.rs) · [Pinned upstream signature type](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/crates/qnero-pqcrypto/src/slh_dsa.rs)

The staged `chain.py:139–149,209–218,313–331,356–379,395–419,456–505` checks each fee, eligible selected anchor, full proof, fresh spent NFs and output CMs. It rejects two nonzero changes to the same asset within one block (including a mint and burn whose net would cancel). Different asset IDs can be updated together subject to block capacity, anchor and cross-slot uniqueness. The mempool uses a separate per-asset conflict check. At attach the same write transaction appends the new registry event, both NFs, both outputs, selected height and one mining reward; the complete public envelope digest also enters the block transition. Replay after a preferred fork removes detached registry rows alongside detached outputs and spent identities; the surviving head determines the authorization/available supply. A valid side-block archive alone has no effect on selected supply. Previously signed or burned transactions may become eligible again on a reverted branch if their current node checks pass. Full atomicity of SQLite and byte-level execution is outside the arithmetic Lean theorem. [Staged node mapping](../funded-conservation/MAPPING.md)

## Wallet policy and inherited history

The standard redemption wallet is stricter than the burn consensus rule. It requires a specific incoming, still-unspent return from the named transaction, fails if that transaction spent a note of the same wallet, and insists that this one receipt has exactly the requested asset/amount. If necessary it can add a second native-only fee note. It pins the returned CM first and expects zero token change. This policy supports matching an external redemption request to a wallet receipt. The C burn predicate permits a funded holder to burn part of owned tokens and carry the rest forward. It does not certify a return to a treasury, a burn for a particular person, fiat payout or its reversal after a chain reorganization. [Deployed wallet logic source](../managed-assets/wallet/redemption.py) · [Redemption semantics](../managed-assets/REDEMPTION.md)

At candidate H13 the B transfer registration becomes eligible, and A ordinary transfers cease at H15. During H13–24, the B parser accepts only transfer opcode zero. Historical A proofs with a genuine nonzero delta remain eligible through H24 under the separate exception. From candidate H25, C is required for **all** consuming singletons. There is no supply counter or authority reset. In the published fixture the selected H24 prefix already has a fixed row (80, revision 1) and a managed row (107, revision 2). The modeled C suffix needs a valid inherited registry and matching funded holdings to draw a historical end-to-end conclusion. The Phase 1B C theorem does not establish those older proof systems. ## Formal boundary

In [Supply.lean](Supply.lean), `Descriptor` contains the wire word, Boolean high bit, 62-bit low part and effective public ID. `Gates.encoded/emptyBurn/publicBinding` correspond to the split, signed-zero rejection and limbwise public selector. `tokenEq/issuerInput/issuerDummy/zeroIdGate` correspond to the sum connection, two issuance-only gates and zero-ID test. Per-note range, tag and dummy gates connect the same four monetary openings. `three_term_bounds`, `issuing_constraints`, `public_selector`, `local_delta`, `selected_supply` and `selected_fee` separate integer arithmetic from the imported funded-opening assumptions. For example, for any currency ID in a selected transition, new holdings plus the burn attributed to that ID equal old holdings plus the issuance attributed to that ID. The native fee is accounted separately.

The concrete `Envelope` is projected to opcode, optional key/signature, predecessor and one opaque inner-packet identity. `Context.opens` and `Wire.sameInner` refer to the **same bytes** used for proof verification, signature verification and effect extraction. `Context.hashInner` denotes SHA-256 of the inner packet and `Context.packetId` denotes SHA-256 of the complete outer packet. `Context.verifies` abstracts signature verification on the typed version-specific message above. The digest value and ID derivation functions are parameters; the Lean kernel does not execute SHA-256 or SLH-DSA. The four constructors `Rule.fixed/register/mint/burn` correspond to the four policy rows above. `registry_delta` computes the exact change of the selected row. `preserve_supply` ties this to the opened-note change; `consistent_path` composes it with ordinary transfers and token-neutral rewards along one branch. This path excludes swaps and A/B proof transitions.

* **Arithmetic and policy.** The state invariant compares outstanding for one ID with the face value in its live, opened notes. The supply gate and local ledger checks above justify the two transitions used in that invariant. Initial consistency, and the true holdings and consumed/fresh identities of the existing notes, are necessary for the corresponding selected-state claim.
* **Authorization.** Signature acceptance is a verifier observation over the exact message, separate from the signer possessing and protecting its secret. Unforgeability, signer/key-message binding, SHA-256 binding of the packet/event ID and the two ID derivations are cryptographic premises. Clearing four high bits produces a 252-bit encoded ID space; domains do not prove disjoint hash images. A registration whose derived ID is zero or already occupied is rejected.
* **Funded witnesses.** Registration bytes identify the fixed predicate and the executable validates the proof. Deriving a satisfying witness from hostile proof bytes, associating its real inputs to unique occupied eligible openings, and preventing NF/commitment aliasing remain outside this source correspondence. Output face value does not establish recipient decryptability or actual possession of the corresponding spending keys.
* **Ordering.** The Python node checks each supply operation against the pre-block selected registry and then writes each event. The one-event-per-ID gate makes a serial per-ID model appropriate for selected blocks. Revisions increment once per nonzero event; one event per asset per height and `h < 2^32` bound a reachable selected revision well below the signed wire's `2^63` limit. The model's per-event arithmetic does not by itself verify consensus fork choice or database rollback.

The released registry functions were also exercised directly against an in-memory SQLite event table: fixed mint/burn refused, managed registration at MAX, extra mint refused, full burn, existing-ID registration/underflow/stale mint refused, and signed-shape current-parent remint to MAX accepted. These function-level checks supplied slot fields directly and do not verify a proof or signature.
