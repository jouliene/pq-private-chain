# Phase 1C — from an accepted packet to a supply transition

**Decision.** The selected registry write can be derived from the original MSP3 bytes, the registered MNG3 verifier's reply and the pre-block registry. For all four operations the derived write agrees with the released validator, including when two assets change in one block. The private side is conditional: accounting for *every* selected output as a live note with a true spend identifier requires a compatible opening for that output. The deployed proof accepts a recipient public-key digest without proving it has such an opening. This prevents an unconditional refinement of the deployed chain into the Phase 1B inventory. No discrepancy was found in the funded cases below.

## One funded partial burn

At H40 two distinct selected commitments belonged to the test holder. Their recipient decrypted them with its own seed. The notes held (10 native, 9 tokens) and (7 native, 7 tokens). A separate rebuild of the selected 84-leaf tree found both occurrences at the root in the eligible header. The header's anchor identifier, the two real nullifiers and their absence from the pre-block spent table were checked. The sorted tree establishes occupied membership under the binding assumptions in the source map. It does not prove a particular chronological input index.

At H41 the node selected the 182,863-byte holder packet `dac03ee85faad7740dd101266c2bf75ee6db5e65c88af9aebeaf44611efc43fa`. Its unsigned MSP3 header selects burn, and its MNG3 word is `2^62 + 12`. The two ciphertexts returned by the verifier are the ones in the packet and in the two new SQL output rows. Opening them gives a zero-value output and change of 14 native plus 4 units of the same managed asset. The token balance equation is **16 − 4 = 12**, and the independently read public supply falls **30 → 18**. The native equation is **17 − 14 = 3**.

A separate fixed registration in that block charged another 3, so the confirmed native reward was **106 = 100 + 3 + 3**. At H42 a signed mint added 2 to the managed asset using the preceding burn transaction and revision 2. The resulting supply was 20 at revision 3. The fresh holder and issuer open all new encrypted outputs during the walkthrough. The ordinary redemption CLI requires an exact return receipt; this experiment uses the released native wallet's lower-level payment constructor with two real owner-controlled notes. Nothing in the validator, registered proof or fee rules changes. ## Four operations and their obligations

For every row below, Lean derives **Gates** from the same decoded descriptor and the finite-field residuals for a projected witness. **Admission** follows from the public freshness and eligible-anchor checks plus the private birth and identity premises. **Wire** ties the decoded sign and magnitude to the reply to this exact inner request. **Rule** is obtained by executing the preflight and registry writer. Treating acceptance as proof of the private premises would be circular. The table gives the operation-specific conditions. The historical and fresh mounted validators executed all four.

|---|---|---|---|
| Fixed registration | Bare envelope, absent ID derived from network and first NF. First input real, no input tokens. Fixed policy, revision 1, supply +q. | H41, 0 token input, 5 output, new row 5. Second supply event in this block concerns a different ID. | Compatible funded fee input and resulting notes, derived-ID binding. |

## How the result is checked

1. **Formal implication.** Lean 4.19.0 checks `selected_refinement` against the imported Phase 1A/1B definitions. The output is a consistency statement about `latest (sqlInsert ...)` and the updated opened-note state. The theorem does not take agreement between the SQL write and the modeled write as a premise. `latest_after_insert` derives that agreement for the modeled SQL operations. `preblock_to_sql` proves that, with distinct event IDs, looking up each row when writing yields the same registry as planning all writes against the parent. The additional `checked_parent_block` theorem lifts supply-only slots through the block in order, with the compatible births and identities required at each intermediate state. `real_occurrences_distinct` rules out using the same funded occurrence twice under those premises. `checked_monetary_effects` gives the asset-ID equality, per-asset delta, native fee and original transaction digest. The miner output and arbitrary mixtures of ordinary payments and swaps lie outside that batch theorem. [Lean source](Refinement.lean) · [Phase 1B theorem](../funded-supply/Supply.lean)
2. **Implementation correspondence.** The original native C registration and its public source pins are checked. A clean database replays the exact blocks using the deployed `Chain.accept`. A passive listener records only the public role's existing call returns. For each of eight selected C events it pairs the *original* packet with its precise inner-proof reply and, for signed operations, the actual issuer request and reply. The Lean executable reconstructs the envelope, hashes, IDs and issuer request, runs the public guards against the actual pre-state and computes the row. The harness compares it with SQL after commit, along with the selected packet, both spent entries, ordered outputs and ciphertexts, other asset rows, and the miner credit. An independent wire reader checks the complete selected store. These comparisons test the source correspondence. They do not formally verify the released Rust/Python runtime or SQLite. [Replay and readback](replay.py) · [Public check](Check.lean) · [Comparison and axiom audit](kernel.py)
3. **Funded private evidence.** The four older H28/H29/H30/H32 packets are replayed from the Phase 1B history. Their private totals come from the earlier, owner-assisted disclosure. Four new supply operations use fresh wallets on the same H33 base. Their consenting wallets reopen their own receipts locally. The fresh burn also supplies its exact two input/output projections to the Lean monetary residual check. An outsider replaying the fixed H42 suffix can verify its original proofs and SQL writes and compare the published private aggregates. Independent decryption of *those exact ciphertexts* requires the original keys. [Earlier private evidence and its provenance](../funded-supply/review/PUBLIC.md) · [Deployed source map](OBLIGATIONS.md)

The fixed suffix contains only the nine original public block bodies H34–42. Its SHA-256 is `d87fe6525f029565844c53563a7fdbc6be71996a07ad3fcee5a6d9c4f1999910`. The reproduction checks the historic H33 prefix, x86-64 C deployment, Qnero source pin and Lean toolchain, and also generates a second suffix with fresh keys. The shared four historic events appear in both passes. A registered proof returning success is an observation. Existence of compatible hidden openings across a malicious history, binding of commitments and the tree, knowledge of spend secrets when required, authorization-key control and signature security are separate premises.

## Reproduction

Use Linux x86-64 with Python 3.10+, Git, curl, zstd, tar and bubblewrap permitted to create unprivileged namespaces. The script creates a new private directory. Seeds, decrypted records, funding links and output true nullifiers stay there. Publish only the allowlisted JSON summaries.

```sh
bash experiments/supply-refinement/reproduce.sh "$(mktemp -d)/case"
```

`funding.json` contains the new case's authorized test disclosures. `trace.json` contains public packet/reply digests and selected registry quantities. `kernel-result.json` lists machine-checked results and the scope of the private residual check. The `fixed/` subdirectory contains the independent wire replay of the pinned case. The release and clean-clone walkthrough are distinct from a mainnet assurance claim.

## Remaining implication

Even granting the exact MNG3 relation and verifier soundness, an arbitrary funded output is created with a witness-supplied recipient digest. Neither that relation nor a fresh public CM proves the existence of an owner key pair assigning a compatible *true* nullifier to the new output. In the current imported model every funded output has one. An asset registry can debit the correct public amount while this mathematical representation of all live, spend-identifiable private value remains unestablished. For controllably generated addresses the separate birth/provenance, cross-era opening, real/dummy separation and binding assumptions are still needed. The next precise proof obligation is an occurrence-based accounting model that records value at birth and justifies a unique spend identity when the occurrence is consumed, or a protocol enforcing the missing output-key property. Neither change is included in Phase 1C. Quantitative post-quantum soundness and joint receipt privacy remain separate research questions. [Exact cryptographic obligations](OBLIGATIONS.md)
