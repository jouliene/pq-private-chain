# SGM1 swap wallet consent before drafting

Each resident wallet derives its 1,632-byte receiving descriptor from its own backup and chain. Its 64-byte spending-owner field and 1,568-byte ML-KEM-1024 encapsulation key are compared in full before the wallet accepts a proposal. The trusted launcher fixes which two local wallet endpoints correspond to the intended maker and taker. It provisions a dedicated point-to-point enrollment channel and closes both ends before launching the coordinator. Only the role-specific request and reply pipes are inherited by the coordinator. Each owner sends the other one public enrollment record containing `SWI1`, its one-byte role, the 64-byte chain identifier, its complete descriptor and its separate 64-byte SLH-DSA-SHAKE-256s preflight public key. Each owner checks the other role and chain and retains its own ordered pair of pins. This local channel models prior authenticated contact between the intended owners. A deployment needs a trusted way to authenticate that contact. An untrusted directory or a coordinator-supplied key cannot establish it. [Launcher](../sgm1-admission/wallet_launcher.py) · [Wallet](../sgm1-admission/swap_owner.py)

The coordinator proposes both descriptors and offers. Each wallet checks its pins, the funded owner, its signing key for this wave, the anchor from its independently replayed ledger and the agreed economics. The exact preflight commitment is FS01 SHAKE256 under the `terms` tag over the following ordered, fixed-width fields. Integer encodings are little endian. A role array is always maker followed by taker.

| Field | Encoding |
| --- | --- |
| Protocol and history | ASCII `SGM1/pinned-swap/v1`, genesis SHA-256 (32 bytes), chain (64), eligible anchor (64), wave (8) |
| Freshness and fee | Salt (64), expiry (8), total fee (8). The maker pays one and the taker pays zero under this version |
| Role identities | Two enrolled preflight public keys (64 each), then two ephemeral final approval keys (64 each) |
| Destinations | Both complete receiving descriptors (1,632 each) |
| Economics | For each role, outgoing asset (64), outgoing quantity (8), outgoing native amount (8) |

Each wallet signs a second FS01 `terms` digest over ASCII `SGM1/pre-draft-approval/v1`, one role byte and this 64-byte commitment. A wallet may accept only one proposal per wave. It requires two correctly ordered signatures against its locally enrolled keys on the same commitment before returning any draft. The draft command takes no receiving instructions. The sender constructs both receipts from its own pins. A bad request aborts that wallet's session. Independently matching signatures prevent one acceptable local view from unlocking a different view shown to the peer. As with any relay, someone can withhold the matching signatures, a draft or the final pair. The protocol makes no fair-delivery guarantee. [Implementation](../sgm1-admission/swap_owner.py)

The extra signatures authorize drafting and remain off chain. Each owner sends one 29,792-byte signature to the coordinator and receives the ordered pair at unlock. Across both request/reply pipes that accounts for 178,752 raw signature bytes per swap, or 357,504 hex characters before JSON framing and other fields. Each direct enrollment record is 1,765 bytes once per wallet process. The existing fresh role signatures still cover both complete ordered transaction cores. Before a final signature, each wallet checks its own core digest, both real public proofs and the exact asset, quantity, native amount and spendability of its incoming receipt. The admitted pair, ledger API, proof and signature fields keep their historical byte layouts. The harness's optional real conflicting ordinary spend requires a separate maker-local one-use startup grant. Both conflict outputs use the maker's descriptor. The default owner rejects that command even after complete preflight consent. [Final approval](../sgm1-admission/swap_owner.py) · [Fixture generation](../sgm1-admission/generate.py)

## Reproduction

The same Linux, Python 3.12, NumPy 1.26.4, Node v24.22.1/OpenSSL 3.5.9, native wide-field Python extension and native SGM1 verifier setup as the admission experiment applies. Export `FS_RECEIPT_NODE`, `SGM1_NATIVE_LIB`, `PYTHONPATH`, `SW_FIELD=gf256` and `OPENBLAS_NUM_THREADS=1` as shown in its build script. Choose new scratch directories. The coordinator sees only the expected public wallet messages. Secret backups, issuer openings and private keys stay out of the check output. [Dependency setup](../sgm1-admission/reproduce.sh) · [Checks](wallet_checks.py)

```sh
python3 -B experiments/sgm1-security/wallet_checks.py /tmp/sgm1-wallet-negative negative > negative.json
python3 -B experiments/sgm1-security/wallet_checks.py /tmp/sgm1-wallet-honest honest --workers 4 > honest.json
```

The negative run checks replacement of the KEM portion under the same owner, replacement of the full recipient, both roles' destination views, split salts and peer keys, role or signature reordering, absent peer authorization, authentic approvals from an independently enrolled earlier session, unauthorized ordinary conflicts, and destination overrides after valid consent. At the coordinator each denied draft or conflict request must receive exactly `{"error":"rejected"}` followed by LF, 21 bytes in total. The check closes the corresponding request pipe and requires EOF without additional reply bytes. A denial therefore carries zero bytes of draft payload. The honest run measures complete successful frame sizes on those same pipes, verifies correspondence between the measured cores and both confirmed swaps, admits every operation through the public native ledger, closes and reopens SQLite and checks the durable tip and database integrity.

The author run exercised 15 negative scenarios with 49 denied draft or conflict requests across the two roles. Exactly 1,029 application response bytes and zero draft payload bytes reached the coordinator. Both independently approved the correct terms before the default-conflict and changed-draft-command controls. [Per-frame negative results](evidence/WALLET_NEGATIVE.json)

The honest author run generated 18 fresh ordinary transfers, two fresh signed two-owner swaps and the separately authorized conflicting alternative. Each of the four successful draft RPC replies carried a 183,360-byte core in a 366,732-byte JSON frame. Their four digests matched the four cores admitted at heights 10 and 20. The durable node reopened with the same tip at height 20, 57 outputs and fees totaling 20 native units. Four prover workers completed the whole run in 282.70 seconds on the author's host. [On-wire sizes, core digests and durable tip](evidence/WALLET_HONEST.json)

These checks assume two honest wallet implementations, proper role assignment at enrollment, intact local OS/process separation, and working cryptographic primitives. Negotiated amounts, offered assets, both descriptors and draft cores are visible to the coordinator after their respective protocol steps. The checks concern disclosure through a substituted receiving key before drafting. They establish neither a network anonymity theorem nor endpoint security against a compromised wallet, launcher or host.
