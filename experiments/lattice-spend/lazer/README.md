# Reproducing the corrected LaZer membership component

This benchmark evaluates the ZK-enabled membership relation from Table 3 of Biasioli et al. The stock in-process author path and the canonical-transcript cross-process variant have distinct results. The latter transports the public messages between processes and runs the upstream reduction and terminal verifier. All test trees are synthetic. The two-input variant checks two distinct paths against one common root of a depth-40 binary tree.

## Relation and interface

A privately chosen leaf is the compression of a binary string of 14 degree-512 polynomials (the Falcon public-key width). The two leaf compression rounds include input length. Each binary internal node commits to the ordered pair of child bit decompositions using a fixed public module-SIS compression matrix modulo 256. Per level the witness contains private direction, sibling, transition and lifted modular quotients. The constraints enforce the delta, the conditional left/right ordering, and a degree-zero binary selector. The public root is 512 byte-sized coefficients. The proof system works over the ring with degree 256 and modulus `2^38−107` by splitting degree-512 ring elements. [Hash and parameters](https://github.com/lazer-crypto/lazer/blob/b958e247a2fdb9593b3c25c9603c6c5305c19420/python/succinct_zkp/hash.py) · [Path constraints](https://github.com/lazer-crypto/lazer/blob/b958e247a2fdb9593b3c25c9603c6c5305c19420/python/succinct_zkp/membership_proof.py)

`stock64` reproduces one ZK-enabled Table 3 instance. As in the upstream benchmark for heights ≥10, it samples the private leaf, siblings and directions and derives the root. It does not build 2^64 leaves. The original multi-path sweep calls this sampler separately per path, deriving a fresh root each time. In `shared40` two independently sampled depth-39 subtrees have their roots joined as left and right children. Both private paths are extended by the opposite subtree root. Both full root recomputations must match before proving. This represents two openings in a binary tree with the same 40 index bits as the deployed tree's 20 four-child levels. The compression function, root width and shape differ from the deployed tree. Full old-state membership, leaf ownership, nullifier derivation, conservation, receipt authorization, issuer policy and swap signatures require additional obligations.

The upstream frontend produces opaque CFFI handles to parameters and proof. Its printed size is a parameter generator's predicted bit count divided by 8192, rounded to two places. No complete network encoder or decoder is exposed. We implemented a bounded, explicitly experimental little-endian x86-64 transport. It carries the Dachshund outer commitment, all active recursive message polynomials, clear JL projections in the noncompressed rounds, all five LNP-Lite messages and the final reduced opening consumed by the verifier. There are no pointers, original leaf/path, original input witness, or prover-chosen dimensions in the transport. Ring elements use three 256-element signed 16-bit limbs each, clear projections use signed 32-bit values, and the final small polynomials use 16-bit coefficients. The four-byte `LZM1` marker precedes a single XZ stream. Widths and vector lengths come from fresh verifier-generated parameters. All measurements include every actual byte of that marker and stream. `root.bin` is a separate 512-byte public input. The decoder limits expansion to 1 MiB, checks the XZ end marker, exact expected array size and absence of trailing bytes, and supports the two fixed synthetic profiles. Encoding is a research measurement; production transport needs a canonical reviewed wire protocol and security review. [Native generation and size print](https://github.com/lazer-crypto/labrador/blob/c1ae0e612d5accd9e7d9d1c264951c1afe949c83/labrados_python.c#L297-L363) · [Recursive verifier](https://github.com/lazer-crypto/labrador/blob/c1ae0e612d5accd9e7d9d1c264951c1afe949c83/pack.c#L386-L460) · [Array codec](arrays.c)


The public envelope is `LMW1 || profile_u8 || registered_descriptor_SHA256 || proof_bytes_u32le || root[512] || LZM1_proof`. Its 41-byte header and single 512-byte root add 553 bytes to the measured compressed proof. The descriptor names the immutable LaZer and LaBRADOR source commits, local transcript revision, degree, modulus, hash tree shape and codec version; its exact deterministic encoding and registered digest are in [frame.py](frame.py). The receiving verifier selects its approved profile locally before reading the frame and rejects mismatched profile IDs, digests, boundaries and trailing bytes. The upstream statement builder starts its 16-byte transcript state at zero and absorbs the packed RHS (including the root), linear coefficients in insertion order, and quadratic coefficient values. The sparse operand indices, norm metadata and degree-zero binding locations are configured by the local constructor; the API does not absorb a serialized complete verification descriptor. An application allowing multiple relations, networks or transaction versions would need to register and domain-separate them explicitly. [Public statement construction](https://github.com/lazer-crypto/labrador/blob/c1ae0e612d5accd9e7d9d1c264951c1afe949c83/labrados_python.c#L57-L295)

## Run

On Linux x86-64, install GCC 13.2 or later, CMake, make, unzip, GMP/MPFR development files, Git and Python 3.12 development files plus pip. The code generator for optional linear-proof demos uses Sage. Membership uses existing shipped parameters and does not invoke that generator. The bundled HEXL build fetches cpu_features `32b49eb5e7809052a28422cfde2f2745fbb0eb76`. Python packages are installed into the chosen build directory. Both BUILD and OUT must be new. Use a single allowed CPU number.

```sh
bash experiments/lattice-spend/lazer/build.sh /tmp/toolkit-build
python3 -IB experiments/lattice-spend/lazer/run.py /tmp/toolkit-build /tmp/toolkit-out --cpu 2
```

The author build used GCC 13.3.0, CMake 3.28.3, CPython 3.12, cffi 1.17.1, numpy 1.26.4, setuptools 75.8.0 and pycparser 3.12. GMP 6.3.0 was system-provided. To build without changing a machine that already has the MPFR runtime, extract its matching development package privately and expose its headers and linker path:

```sh
mkdir /tmp/toolkit-headers && cd /tmp/toolkit-headers
apt-get download libmpfr-dev
dpkg-deb -x ./libmpfr-dev*.deb sysroot
export CPATH="$PWD/sysroot/usr/include"
export LIBRARY_PATH="$PWD/sysroot/usr/lib/x86_64-linux-gnu"
ln -sf /usr/lib/x86_64-linux-gnu/libmpfr.so.6 "$LIBRARY_PATH/libmpfr.so"
cd -
```

The native command requires the Tiger Lake instruction subset including AVX-512 and AES. On this i7-8700K host use Intel SDE 10.13.1 in Tiger Lake mode. The Linux archive SHA-256 is `94e97d623fec54385686e1e7ba65ebc9941748c05ee451423948334892bf2b50`. SDE executes the actual compiled instructions and gives wall time, CPU time and memory use specific to emulation. The authors' one-core i7-11850H median for the single-path ZK depth-64 row is 1.80 s prover and 0.90 s verifier. These are their native measurements. [Intel SDE](https://www.intel.com/content/www/us/en/download/684897/intel-software-development-emulator.html) · [Table 3](https://eprint.iacr.org/2026/1289.pdf)

```sh
curl -fL https://downloadmirror.intel.com/924984/sde-external-10.13.1-2026-07-28-lin.tar.xz -o /tmp/toolkit-sde.tar.xz
sha256sum /tmp/toolkit-sde.tar.xz
tar -xJf /tmp/toolkit-sde.tar.xz -C /tmp
python3 -IB experiments/lattice-spend/lazer/run.py /tmp/toolkit-build /tmp/toolkit-out \
  --cpu 2 --sde /tmp/sde-external-10.13.1-2026-07-28-lin/sde64
```

A run writes unmodified role logs, each framed public proof and root, and aggregate metrics in OUT. Replay a published public frame on the same build with `run.py BUILD NEW_OUT --replay experiments/lattice-spend/lazer/public --positive-only` plus the same CPU/SDE flags. This path requires only the frame, which embeds the root. For the paper-recommended September source pin and original authors' unmodified in-process path use `build.sh NEW_STOCK_BUILD --stock` followed by `run.py STOCK_BUILD NEW_OUT` and the CPU/SDE flags. This executes the authors' own `benchmark_membership_proof(64, 1, True)`, including their in-process verifier. The published stock record contains successful proof emission followed by rejection in a fresh process. The canonical profile demonstrates independent constructor agreement through positive cryptographic verification of the actual serialized file. The verifier assembles every public equation from the root and skips the private inserts. It never calls the path sampler or prover. Wrong-root and changed-terminal-coefficient controls use the same real verifier. The latter recompresses a changed coefficient so the verifier must decide cryptographic validity. `whole_process` includes imports, public statement generation, emulation, the named role and teardown. `params_and_prove` times the authors' parameter generation plus prover; `verify` times only the real cryptographic verifier. The remaining frontend work, proof encoding, and decoding have different scopes. Public test fixtures use deterministic Python randomness for the synthetic tree only. Native proving randomness comes from the OS.

## Assurance boundary

The toolkit combines Dachshund, LaBRADOS, LNP-Lite, further LaBRADOS rounds, LaBRADOR, and a terminal norm-checked opening. Its C selector uses the root-Hermite factor 1.00444. The seven-polynomial MLWE dimension for the chosen 38-bit modulus corresponds to 1,792 coefficients; the code comments estimate a primal uSVP BKZ block size around 394. The paper's Appendix E hash estimate concerns collision resistance of the particular compression relation alone. Appendix B.4 describes composed noninteractive knowledge soundness heuristically in the classical ROM, with loss depending on oracle queries. The implementation uses 128-bit challenge seeds and a 16-byte chained SHAKE128 transcript. A 128-bit work factor for quantum extraction of a funded spend is unestablished here. [Ring and challenge constants](https://github.com/lazer-crypto/labrador/blob/c1ae0e612d5accd9e7d9d1c264951c1afe949c83/data.h) · [Selector and transcript](https://github.com/lazer-crypto/labrador/blob/c1ae0e612d5accd9e7d9d1c264951c1afe949c83/proofsystem.c#L103-L118) · [LNP parameters](https://github.com/lazer-crypto/labrador/blob/c1ae0e612d5accd9e7d9d1c264951c1afe949c83/lnp.h#L14-L27)

Appendix C of the revised paper proves a hardness result for the **unstructured** multi-secret extended LWE problem; the simulator instantiation relies on its two-secret module analogue with a jointly leaked rejection sign. The subsequent LEASH paper (19 November 2026) investigates completeness, recursive reduction and extraction issues in LaBRADOR and proposes changes. The available toolkit C revisions precede it. An independent mapping of LEASH's preconditions and proposed repairs to the full corrected composition, reparameterization, the noninteractive quantum setting, and receipts/seed-recovery security are open. Empirical acceptance, rejection and wire size give no substitute for those obligations. [Revised toolkit](https://eprint.iacr.org/2026/1289) · [LEASH](https://eprint.iacr.org/2026/2898)
