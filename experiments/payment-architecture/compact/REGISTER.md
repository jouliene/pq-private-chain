# Registration MP10

Use Esgin, Steinfeld and Zhao's [MatRiCT+ reference implementation](https://gitlab.com/raykzhao/matrict_plus/-/tree/b24f3176d2db15ca55d91c8c9cbe1cef201c5d2d/n10), revision b24f3176d2db15ca55d91c8c9cbe1cef201c5d2d, archive SHA-256 88c96feae3dafc513e2d2f15978730ee7000741840db0e7f83a09e302384587c. Run the native n10 algorithms with two inputs, two outputs, 10 public pairs, 256 coefficients, q = 167770241, qhat = 3489661057, r = 64, W = 44 and two 32-byte serials. Use a fixed public setup seed and fresh secret randomness per invocation. Use OpenSSL's FIPS 202 SHAKE256, with a known-answer cross-check, as the implementation of the source's three SHAKE256 calls. Do not change the upstream lattice, transcript, acceptance, or Gaussian algorithms.

Execute three honest payment-core authorizations. First spend a pair of fresh coins. Retry against another public ring containing the same pair. Independently fund the same two address keys again and authorize the distinct new commitments. Verify each in a fresh process with only the public ring and encoded public values. Test canonical, bounded coefficient serialization and exact verification after decoding. Measure candidate row intersections for refresh, serial uniqueness across distinct funding and output key visibility. Check an independently altered public statement and proof are rejected.

The baseline candidate preserves exactly the implementation's zero-fee equality. Price an integrated format with a fixed registered profile, selected branch anchor, public fee, ring-wide public position references, two public serials, two output accounts and two independently encrypted offline receipts for coin openings. Call out the missing positive-fee relation, offline reusable stealth-address construction and receiving-key recovery if they survive examination. Do not substitute one-time privately handed-off public keys for the accepted public offline-address semantics. A lattice core passing round trips or an attractive size does not authorize a devnet integration. Compare the authors' strengthened compression separately from the lossless encoder over their actual C verifier.
