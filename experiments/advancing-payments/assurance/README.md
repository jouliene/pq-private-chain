# APV2 assurance and registration

Before funding or proving, register a new source-built profile at every recursive layer. The candidate uses original Poseidon with Goldilocks EF2 for proof commitments and Fiat–Shamir. The prior native experiment used the stock conjectured FRI target of 100. The APV2 constructors request 128, increase queries from 28 to 43 at rate 1/8, and remove 16-bit grinding. This changes the complete proof pipeline. It does not establish a 128-bit security rating for a private payment.

| Registered layer | Public inputs | Wires/routed | Row blinding and FRI leaf hiding | Child fixed in circuit |
| --- | ---: | ---: | --- | --- |
| Spend leaf | 26 | 143/80 | Off; raw proof confined to its originating wallet | Registered payment constraint system |
| Wallet, one leaf | 26 | 135/60 | Both on | One registered nonhiding spend proof |
| Occupancy 2 / 3 / 4 | 54 / 80 / 106 | 135/60 | Both on | Exactly 2 / 3 / 4 registered wallet proofs |

All layers use two PLONK challenges, two configured constants, base arithmetic gates, maximum quotient degree factor eight, FRI rate bits three, cap height four, and ConstantArityBits(4,5). Each outer proof publishes the version tag, occupancy and all per-wallet public fields in order. Each recursive verifier has the child's verifier-only data as circuit constants and the installed child's common data when building targets. A valid parent proof under a substituted inner circuit could otherwise establish a different statement. The new registry is separate from the original release verifier bytes and profile ABI. ## Meaning of the numbers

The exact verifier/prover dependencies are qp-plonky2, -core, -field and -verifier 1.5.5 from the pinned Qnero lockfile. In this fork `CircuitBuilder::check_config` computes `min(bit_length(p²), q × rate_bits + grinding_bits)`. It explicitly calls this a conjectured FRI test. With `p=2^64−2^32+1` the integer bit length of p² is 128 and its logarithm is 127.9999999993. The old query/work term is 100; the new term is 129 and the extension caps the implemented screen at 128. The no-grinding proof has a public proof-of-work field but its threshold check asks for zero leading difficulty bits. The raw query term alone increases from 84 to 129. This gives no generic factor-of-2²⁸ improvement for every underlying adversarial strategy. In particular, removing grinding changes the transcript search cost and strengthening the query schedule leaves every algebraic/hash assumption in place. [Configuration check, pinned crate](https://docs.rs/crate/qp-plonky2/1.5.5/source/src/plonk/circuit_builder.rs) · [upstream Qnero profile](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/docs/CRYPTOGRAPHY.md)

Fiat–Shamir absorbs effective FRI parameters, the circuit digest, public-input hash and wire cap before the first PLONK challenges. Later stages absorb the product and quotient caps, openings, FRI commitments, final polynomial and proof-of-work witness. The verifier samples two base-field betas, two gammas and two alphas from the Poseidon transcript, and samples zeta in the quadratic extension. These draws and a roughly 128-bit extension cardinality do not bound the full algebraic error at 2⁻¹²⁸. Degree factors, polynomial/register identity tests, binding, lookup and PLONK constraints, recursion depth, adaptive choices, multisession use and the concrete FS compiler have to be included. [Pinned challenge schedule](https://docs.rs/crate/qp-plonky2-verifier/1.5.5/source/src/plonk/get_challenges.rs)

Counting proof invocations alone gives 2k+1 instances in the expansion of one k-wallet outer payment; even a hypothetical independent per-instance uniform upper bound would incur a union-bound factor up to nine at k=4. A fleet of 100M chosen payments also requires an explicit multi-target/query model. Those are accounting examples, not assigned security probabilities.

The fixed `PoseidonGoldilocksConfig` implementation has **both** `Hasher` and `InnerHasher` set to the original Poseidon hash. Width 12, x⁷ S-box, eight full and 22 partial rounds, four-field-element (~256-bit) digest. The maintainers cite an algebraic estimate around 95 bits for this parameter choice. It is a warning about the hash assumption, not a measured 95-bit payment forgery. An *ideal* 256-bit hash has generic quantum collision-query scale roughly 2⁸⁵·³, distinct from its roughly 2¹²⁸ preimage scale and from concrete circuit cost. Which property is needed depends on the binding/Fiat–Shamir reduction; these ideal benchmarks neither prove security nor instantiate a whole-protocol attack. Original Poseidon remains inside every recursive verifier. Changing only the archival file digest, ledger hash or outer transcript cannot repair an inner assumption. Replacing the proof hash or using a larger extension requires compatible recursive gadgets, new common/verifier data, measurements and a version migration. [Pinned hash implementation](https://docs.rs/crate/qp-plonky2-core/1.5.5/source/src/config.rs) · [fork security analysis](https://github.com/Quantus-Network/qp-plonky2#security) · [BBLP analysis](https://tosc.iacr.org/index.php/ToSC/article/view/9850) · [generic quantum collision-query bound](https://arxiv.org/abs/quant-ph/9705002)

The published WHIR profile instead uses Goldilocks EF5 (~320-bit field), SHA3-512 commitments, SHAKE256 and a reported 130.490-bit interactive error calculation with explicit list/guard accounting. CMS-style quantum compilation has query-budget-dependent losses even if the concrete compiler matches its theorem. For illustration, using the reported interactive number in the quadratic query term makes that sufficient bound vacuous near 2⁶⁵·²⁵ queries. APV2's 128 is a different conjectural constructor check; it cannot be inserted as a proven round-by-round knowledge error into that transfer. Neither experiment proves stronger complete PQ assurance than the other. [WHIR joint transcript and CMS qualifications](../../wallet-created/structured/ASSURANCE.md)

## Privacy and application binding

The outer payer-facing artifact that leaves each wallet must hide the raw leaf proof. The raw leaf commits unblinded wire observations and cannot be treated as a private submission even with an honest builder. At the two hiding layers the fork bases the random-row allocation on the actual FRI queries/reduction arities, extension degree, final polynomial length, and openings at zeta and g·zeta. The prover salts each wire, permutation/product and quotient oracle leaf with four random field elements, in addition to row blinding; the same effective FRI hiding flag is consumed in both proof parsing and recursive verification. Changing q affects the opening budget and therefore potentially circuit degree and bytes, not just the number of Merkle paths. These are source facts. A joint, adaptive, multi-theorem simulator for the real packets, query commitments, recursive transcripts and receipts under concrete hash assumptions remains unestablished. The hiding wallet wrapper takes the raw leaf proof as its private witness. Only the wrapper and its public effects leave the originating wallet. [Builder’s blinding allocation](https://docs.rs/crate/qp-plonky2/1.5.5/source/src/plonk/circuit_builder.rs) · [oracle construction](https://docs.rs/crate/qp-plonky2/1.5.5/source/src/plonk/prover.rs)

Wallet submissions, serialized proofs/ciphertexts and outer public inputs remain observable. A builder or observer that saw the incoming public packets can associate them with their slots by the forwarded values and ciphertexts. Network source/timing, occupancy, anchor/age, note output count, fee and nullifiers are visible. The note/tree layer uses Poseidon2 domain-separated digests, the KEM uses ML-KEM-1024 and encrypted notes use ChaCha20-Poly1305 with a protocol-specific KDF/context. Standardization of the KEM's confidentiality property does not prove recipient anonymity, post-compromise secrecy, sibling/slot unlinkability or adaptive receipt-proof composition. Fresh keys and coins, canonical encodings, authentication before note use, no double application of spent identities and authenticated history all remain required. The leaf takes the ciphertext digest as a free public input; the public verifier checks it against the submitted bytes. This binds the bytes supplied by the payer. The circuit does not establish that they encrypt the constrained opening to the intended payee. An honest sender and a receiver controlling only incoming notes can demonstrate actual delivery and subsequent spending. A restored, previously funded wallet can instead choose its own earlier change; that respend alone cannot establish external receipt provenance. The dedicated receiver test needs an initially unfunded wallet, two independently recorded incoming notes, and fresh seed-only scan plus verified spending of those notes. [Incoming-only receiver control](../incoming_only.py) · [leaf relation](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/crates/qnero-circuit/src/circuit.rs) [Qnero application assumptions](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/docs/CRYPTOGRAPHY.md) · [NIST FIPS 203](https://csrc.nist.gov/pubs/fips/203/final)

For correctness, proof validity only authenticates the declared relations at their chosen anchor. The node must independently resolve each height/hash against its own current branch and retained-eligibility window and check current spentness and uniqueness across slots. Every original nullifier/commitment/ciphertext binding, fee and state transition must survive replay, rollback and reorg. The sorted quaternary tree alone does not certify a position or the selected historical chain. An authorized local genesis and a publicly checkable transition history establish the test's funding boundary. Token and two-party swap rules need their own registered relation and atomic admission; the ordinary 26-word slot proves neither feature. ## Independent inspection

The registrar generates the combined, common and circuit-specific verifier-only artifacts from installed sources before proving. Use an independently approved digest for `profile.json` and keep the configured registry read-only for wallets, builders and nodes. A self-consistent set of files or an untrusted sender-supplied manifest does not authorize a new program. An existing database must reopen under its authorized genesis and deployment profile; migration/activation needs an explicit version decision.

`check.py` parses the actual fork verifier-only cap and canonical limbs, circuit configuration, effective FRI settings, trace/FRI dimensions and derived reduction arities, public-input count, and hiding flags. It verifies that the pinned combined bytes split exactly into verifier-only followed by common data and that all 15 BLAKE2b-512 identifiers match the approved registry. Remaining gate-serialization bytes are covered by the exact digest; their mathematical equivalence is a circuit/source-review obligation. The historical stock artifact is an executable control: it decodes as 100/28/16, target/query/grinding, and is rejected as APV2.

```sh
python3 -I -B experiments/advancing-payments/assurance/check.py --stock experiments/wallet-created/qnero/evidence/public/private-verifier.bin
python3 -I -B experiments/advancing-payments/assurance/check.py --registry "$registry" --approve-manifest "$approved_sha256"
```
