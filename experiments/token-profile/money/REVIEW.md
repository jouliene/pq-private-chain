# Monetary constraints at the native-token boundary

DLF1 authorizes a transfer of **one integer quantity**. Adding a token label to a receipt, commitment wrapper, proof selector or D8 archive key leaves that equation unchanged. A token needs an authenticated origin and a spend relation that conserves token and native units separately. A recipient must be able to reconstruct the same typed commitment from the encrypted opening. This is a design/source review of repository revision `9c21c2b4297657b8c4cca219c4c480910557d00e` and Qnero `f04c91307837c0231668383bec76ba98d89d2652`.

## What the existing native path checks

| Location | Actual obligation |
|---|---|
| DLF1 input | A Boolean selects dummy or real. Dummy value is zero. Real membership is gated by that bit. `pk = H(PK, H(AK,ask), nk)` feeds `inner=H(NOTE,pk,rho,r)` and `cm=H(CM,inner,value)`. Real nullifier `H(NF,nk,rho,r)` has the same hidden key and opening. Dummy uses `NF_DUMMY`. Both nullifiers are published and must differ. Non-padding anchor implies at least one real input. Domain separation depends on hash security. |
| DLF1 path | Each real note's recomputed commitment reaches the header's private tree root. The two paths share a bounded depth (0–20); the circuit hashes 4-ary nodes with private position hints. The off-circuit implementation sorts children and supplies hints. Membership and ownership are proved. The circuit does not expose a selected-chain leaf index, note count or leaf position. Public anchor and height must be checked against the node's eligible branch. |
| DLF1 output and fee | Both amounts, both input amounts and public fee are independently 62-bit range checked. The output seed is derived from **both** published nullifiers and output index, and the commitment is recomputed using that seed. The one enforced sum is `in0+in1=out0+out1+fee`. The registered inner has 26 public field words. |
| Native verifier and ledger | Native codec enforces fee exactly 3, two distinct nullifiers, distinct nonzero commitments and hash of both ordered canonical receipt bytes. Chain compares anchor/height against branch window, checks spentness and commitment uniqueness in batch and against prior state. Its frontier appends all payment commitments then a public miner reward for subsidy plus native fees. Reorganizations restore selected-path membership and spentness. |
| Receipt | The inner circuit registers the external ciphertext digest as public input and performs no encryption or recipient-decryption check. The verifier compares externally recomputed ciphertext digest. Recipient trial-decrypts and recomputes the expected commitment under its own keys. An accepting proof authenticates the submitted bytes but gives no delivery guarantee against a payer constructing an unusable ciphertext. |

## Integer bounds for the next relation

Write `M=2^62−1` and `p=2^64−2^32+1`. For nonnegative, range-checked inputs, a field equality between integer sums implies equality over the integers when **each side** is strictly below `p`. The original leaf has left bound `2M`, right bound `3M`, so this argument applies even before the protocol limits fee to three. A comment in the upstream note definition suggests a four-term bound. In fact `4M−p=4,294,967,291`. Any new lane with four independently variable 62-bit terms on one side needs another bound, an exact checked carry representation, or smaller amounts. Three such outputs plus a fixed fee of three still fit. The total across different assets never enters a valid per-asset equation. [Upstream quantity range](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/crates/qnero-note-core/src/note.rs#L7-L20) · [Computed maxima and key hashes](BOUNDS.json)

For scalar typed notes and one non-native transfer, choose a common token identifier `T` and require `T ≠ NATIVE`. Under a fixed-role shape one token input and one native input can fund a token recipient, token change and native change. Constrain asset identities on every opening including zero-valued outputs. The independent equations are `t_in = t_pay + t_change` and `n_in = n_change + 3`. This 2-in/3-out shape accepts only one input coin of each kind. Larger fragmented balances need either a consolidation process or more input slots. Reducing this scalar configuration to two outputs is viable only under a documented restriction such as exact funding of one change, or a different fee mechanism. The position of each asset role is visible if roles have fixed publicly distinguishable order. A hidden asset identifier cannot conceal membership of a known one-token universe.

The **candidate selected for testing** is a two-component note. It carries `(native_amount,token_amount)` for a **single protocol-fixed token**. Then a 2×2 spend can return the payer's two residual balances in one note and pay a recipient. Constrain **both** coordinates in every real input and every output, both zero in every dummy, and enforce two independent sums with fee 3 appearing only on the native side. Both left sides are at most `2M`; the right sides are at most `2M` and `2M+3`. Substituting multiple arbitrary token IDs for the single fixed lane requires more constraints. With scalar arbitrary-ID notes, a sufficient generic rule is to enforce the masked quantity equality for every distinct label occurring in **either** input or output plus NATIVE. Equality indicators must be constrained as functions of canonical complete identifiers, including the output-only case, and all lane counts must meet their field bounds. Comparing the grand total or checking a prover-selected subset of labels establishes a weaker relation.

### Consequences of selecting vector notes

Both balances belong to one recipient, share a single commitment and are consumed by **one real nullifier per note**. Derive real spend authority from the same secret key material used to construct the committed public key. Typed derivation must distinguish the version/network wherever identities would otherwise be ambiguous; if multiple spend actions consume the same member note they must produce the identical serial. Derive each new output seed inside the circuit from every input serial and the output slot (with a typed domain). Real and dummy nullifier functions use distinct domains; one dummy must constrain both lane amounts to zero and skip only membership. A valid transfer anchor must consume at least one real note. Zero-value change can still create a note; it cannot create either asset.

For payee vector `(x,y)`, selecting two input vectors with coordinate totals `(N,T)` requires `0 ≤ x,y ≤ M`, `0 ≤ N−x−3 ≤ M` and `0 ≤ T−y ≤ M`. A sufficient grand total balance in the wallet does not ensure a suitable pair exists, or that both changes fit one note. A token-only recipient with zero native must acquire a same-network native fee input before re-spending. Native-only sends use `y=0`, still range check and conserve the other lane, and may need to carry token change from a mixed note. Fixed public slot counts and common transaction encodings are compatible with hiding each payment’s lane activity. They disclose the network’s possible two assets and permit ancillary inference from a small or public funding set. Spending a mixed note reveals one public nullifier, consuming both balances; it must not expose two independently spendable lane claims.

In the reviewed TKN1 implementation the typed opening is `r′ = Poseidon2(0x544b4e310001, token, raw_r[0..4])`, a four-limb digest. All four limbs are connected to the existing `r` targets on **both inputs and both outputs**. Thus the original inner note hash and real nullifier consume that same typed opening. The established Qnero output-rho rule is reused with both nullifiers and output index; it has no new TKN1 domain. Network isolation comes from the typed opening, registered proof program, approved start inventory and authenticated chain context. The updated candidate allows one or two real inputs. It constrains `token[i] × is_dummy[i] = 0` in addition to the inherited native constraint, and connects the public fee to the constant three. The native upper bound and new input/output checks hold even with one dummy. The previous design sketch that required two owned inputs did not enter registration. The wallet checks both change bounds. Its small test selector takes the requested prefix of the available notes; a production wallet would need to search for a usable selection. [Candidate circuit](../candidate/profile.rs) · [Candidate wallet](../candidate/wallet.rs)

A receiver’s incoming viewing key contains its public note key and ML-KEM decapsulation key. Receipt encryption and decryption check the expected recipient key, and the scanner reconstructs the typed commitment. The note opening and incoming viewing key do not reveal the spend-authorizing `ask`. An independently generated recipient spending seed derives `ask`, `nk`, its same note key, and a matching KEM keypair. Only the **spending** authority plus an eligible unspent member can authorize the successor; the original payer knows the information it put in the opening but lacks the recipient’s secret authority. Under the hash and KEM assumptions these are independent roles. The strengthened claim that a recipient can spend from received funds requires a positive native balance for the fee and direct full verification of its successor. A payee’s ability to open a single receipt establishes neither. [Wallet spending/viewing key separation](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/crates/qnero-notes/src/keys.rs) · [Candidate receipt codec](../candidate/pair_codec.rs)

The public calculator also checks an illustrative inventory with 53 native and 70 token units. A token-only recipient receives 17, combines that note with 4 native units, and pays another recipient 12 tokens. The two fees of 3 enter a public native fee sink. Final spendable total is `(47,70)`; including the sink reconciles to `(53,70)`. All values are deliberately public constants. ## Issuance, versioning and custody of value

A transfer cannot bootstrap a token supply. Define a single authorized supply source bound to this network and token identity. If initial distribution is public, commit the declared amount, token ID, destination commitment and issuance rule, and check that the amount and asset inside the commitment are the authorized ones, through verifiable construction or an issuance-specific proof. If mint authorization is a consensus nullifier or unique issuance ID, persist and roll it back atomically. Any future token mint must conserve native value; a future miner reward can carry only the native amount authorized by that network. Burn or other minting, if supported, each require its own rule. With transfers conserving each asset, the supplied TKN1 history gives the inductive equations `native_unspent + native_fee_sink = initial_native` and `token_unspent = initial_token`. A network that instead credits miner fees and emits subsidy must account for those distinct flows under its own rules. Here “unspent” includes outputs for which a recipient may have lost the key or received unusable ciphertext. Hidden amounts prevent a public node from independently summing plaintext UTXOs; the inductive result rests on validated issuance, range, authorization, conservation and one-time consumption.

Versioned note commitments must bind asset representation and canonical quantity to ownership and opening at both creation and consumption. A version inferred solely from untrusted packet bytes gives no authentication. A legacy native note consumable from multiple relations must reconstruct its original `cm` and **the same real nullifier** in every relation. The chain shares one selected spent set across these paths. A rule that changes nullifier domain with spend action would lose that invariant. In particular the TKN1 typed randomness is an inner opening of the existing outer native commitment convention. Origin of a new member matters: this argument assumes every accepted creator of a leaf, including genesis, enforces both lanes. A migration must authenticate which creation relation inserted each historical coin or prove its authorized typed conversion. Sharing a root across historical untyped creators would invalidate that induction. If the design places typed notes on a genuinely separate network, state the bootstrap and avoid implying old-chain funds are spendable there. An arbitrary 32-byte asset ID cannot injectively fit four Goldilocks limbs by modular reduction. Use a canonical field digest namespace or an exact byte-to-field encoding such as eight checked u32 limbs. A free u64 identifier likewise needs two u32 limbs or a defined restricted canonical subset. Amount and type encodings in the wallet, issuance, ledger and proof must agree. [Digest canonical decoding](https://github.com/DigitalGuards/qnero/blob/f04c91307837c0231668383bec76ba98d89d2652/crates/qnero-note-core/src/digest.rs)

The selected research network uses explicit synthetic start inventory. Bind the exact inventory root, count, issuance-policy version and token namespace to the genesis/network descriptor, with distinct bootstrap output seeds or a dedicated deterministic allocation rule. If opening values are not available for public recomputation, a preconfigured list of opaque commitments trusts its creator for both balances; record this as a research allocation, or supply a genuine opening-to-allocation proof before treating a public supply cap as verified. Count its native vector component as test-only initial allocation. This test network has no block subsidy or miner fee credit. Ordinary new blocks add three native units per payment to an unspendable fee sink and issue zero native and zero token. Under a fixed no-further-mint policy the token cap equals the validated total in that synthetic inventory. The production/native DLF1 zero-premine history, its subsidy rule and current spent set stay separate. No bridge, main-chain issuance, general asset registry, redemption, subsequent mint authority or fungibility with existing native currency follows from this experiment. A registry for multiple issuers would have to define unique canonical IDs, issuance authority or capped schedule, collision handling, branch activation, exact supply and rollback per asset. Its conservation proof needs the generic label rule above or an explicitly fixed coordinate per new asset.

The native Qnero ciphertext **already** encrypts an eight-byte `asset_id`. `encrypt_note` sets it to zero; `decrypt_note` requires zero and reconstructs an untyped native `Note`. The field could carry a versioned scalar identifier or a second bounded quantity while preserving payload length, depending on the approved profile. The wallet must authenticate the version, reconstruct the exact new commitment and restore/spend through the new relation. Both `NotePlaintext` and `NotePayload` debug printers currently expose `asset_id`; a private-ID or private-quantity use must redact it. Simple presence of this field in a ciphertext does not change current consensus. ## Registered TKN1 and public test genesis

The registered TKN1 verifier is 1,481 bytes, SHA-256 `f4b865c6c2aaa9afdd6a7a7ecb94fe9b76ffdc75d25d5a570cf595d315576c2b`. Native and TKN1 verifier serializations have the same byte length and distinct keys. The reported 468 pre-blinding gates (455 in DLF1) yield 4,096 trace rows, five quaternary FRI folds and 26 public elements. The independent check compares the released key bytes, registered construction specification and compiled-source fingerprints against the delivered source. `load` reconstructs the full TKN1 verifier from fixed code before accepting an operator key. Public verification needs a trusted executable or a prior matching source build. An expected binary hash supplied by the same untrusted party as the executable would not authorize it. [TKN1 registration](../candidate/evidence/REGISTER.json) · [Build receipt](../candidate/evidence/BUILD.json) · [Typed profile](../candidate/profile.rs) · [Common key decoder](../parameters.py)

At bootstrap the operator approves SHA-256 of the complete 488-byte genesis separately. The four fixed rows each carry index-derived context32, recipient public key32, native u64, token u64 and commitment32. The native public helper recomputes both `rho` and raw opening randomness from the first 80 bytes under distinct `TKN1/genesis/...` domains and derives the typed commitment. The node checks all four against exact expected vectors `(100,70),(100,50),(100,70),(100,50)`, the correct context and distinct nonzero commitments. The derived root enters the genesis AP header and the state/body digests include the full approved genesis. The network identifier binds the TKN1 circuit, 22-bit work and eight-height window. Two allocations with different recipient keys would have different approved genesis identities and roots even though they share that network identifier. This publicly checkable bootstrap gives the exact starting cap of 240 tokens and initial 400 test native units, without a mint key. Public openings let participants see the initial assignments; the spender still needs secret `ask` and `nk`. [Bootstrap, transition and native fee sink](../candidate/ledger.py) · [Public commitment helper](../candidate/wallet.rs)

Each successor verifies its complete TKN1 authorization, the branch anchor at the declared eligible height, fresh nullifiers/outputs, exact fee, correct body commitment and recomputed typed root. It checks its own SHA-256 proof of work. The provided implementation processes a linear ordered history in memory. It names the prior AP header hash, which does not include the prior PoW nonce; valid alternative seals for the identical historical header have the same descendant parent identity. This exercise establishes authenticated transfers and per-block work in the supplied stream. Heaviest-fork selection, durable reorg handling and token chain synchronization would need their own test. Receipt-level exceptions and typed-opening mismatch are discarded locally while the authenticated CM still advances the wallet tree. Model totals and wallet restore results from the construction run are separately visible from its public replay. [Candidate validation and receiver walkthrough](../candidate/campaign.py)

## Historical verification

D8C1 verifies eight inner proofs with one baked-in DLF1 verifier and exposes `2 + 8×26 = 210` public words, including tag and active count. Its builder checks exact key derivation; the public role pins both native verifier objects. It admits the native effect shape and its two receipts per active slot. Even a token circuit with identical arity and public-input count changes the verified relation and its verifier digest. Historical native certificates remain native. A token candidate needs a new proof/codec version, distinct registered keys, and a network/effect identity binding the authorized profile, exact public effects and ordered receipts. Homogeneous versioned certificates are simplest. Any mixed wrapper needs constrained dispatch to fixed, registered inner relations, authenticated type for each slot, a canonical padding rule and a lossless mapping to historic ordered effects. A finalized historical certificate then replaces source authorization only under that version’s actual PoW core and proof-of-knowledge assumptions. Issuance/reward and branch checks still apply during replay. Never infer compatible archival size or soundness parameters just from an unchanged number of public words. ## Reproduce the public checks

From the repository root run `python3 -IB experiments/token-profile/money/check.py`. The script calculates interval bounds with exact integers, checks the native release registry, and checks the registered TKN1 key, dimensions and built source fingerprints. Add `--upstream PATH_TO_QNERO_AT_f04c913` to include the source fingerprints and compare the complete JSON with `BOUNDS.json`. This check uses public parameters, installed key bytes and optional source files. It creates no payment proofs or witnesses and does not establish that a future token circuit enforces these invariants.
