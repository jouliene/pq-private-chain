# FS01 fresh-genesis relation

FS01 is a candidate for isolated comparison at revision `7d588784`. A bit-oriented VOLE-in-the-head prover and a ZKB++/Unruh prover can encode the same function independently. The release's profile C, C-to-N7 bridge and registries keep their existing rules. The executable here is a clear monetary oracle, fixed-supply funding prefix, and real receipt/signature components. Neither candidate has an admitted FS01 payment. [Reference evaluator](relation.py) · [Encoder](envelope.py) · [Funding check](issuer.py)

## Typed encoding

All integers are unsigned little-endian. A digest is 64 bytes. Concatenations have exactly the widths below. H(tag,...) is FIPS 202 SHAKE256(0xf1 || tag:u8 || fields, 64 output bytes), using Keccak-f[1600], rate 136 bytes and capacity 512 bits. Tags 1 through 21 in ascending order are ask, kem_seed, owner, cm, leaf, empty, parent, nf, dummy_nf, auth, intent, occ, credit_occ, asset, funding_id, terms, pair, ad, descriptor, chain, issue_body. On a rate boundary padding consumes a fresh block. A 64-byte squeeze fits the last absorb block. FS01 circuit bits within bytes are least significant first. The 0xf1/tag domain belongs only to FS01. [FIPS 202](https://csrc.nist.gov/pubs/fips/202/final)

Use a fresh public 64-byte network nonce and 64-byte policy identifier pinned by the founding manifest: chain = H(chain,nonce,policyID). Independently pin the entire genesis (including ordered transparent grants) in bootstrap. This order lets wallets derive keys before grant commitments are made. One backed-up account uses 64 independent uniform random bytes. ASK = H(ask,chain,backup); A = H(owner,ASK). KEM key generation uses all 64 bytes H(kem_seed,chain,backup) as d || z; the derived KEM and monetary secrets stay separate. The single immutable address codec is ASCII FSA1 || chain64 || A64 || ML-KEM-1024.ek1568 (1,700 bytes). Receipt helper pipes pass the local chain separately and accept only its 1,632-byte descriptor body. New accounts require their own backups. [Receipt implementation](receipt.mjs)

Plain note = A64 || native:u64 || asset64 || qty:u64 || salt64 = 208 bytes. Fresh independent 64-byte salt per output. CM = H(cm,chain,plain). ID zero is native-only. A note with qty zero has zero ID; a positive qty uses a nonzero ID. Native and one user asset can coexist. Receipt, creation, opening, conservation and further spending use identical bytes.

The ordered depth-40 binary tree has empty leaf H(empty), occupied leaf H(leaf,O64,CM64), and parent H(parent,level:u8,left64,right64) at levels 0..39. Padding uses recursively computed empty subtrees. The state authenticates count and root together. Headers must bind chain/height/branch/root/count, history and work with a suitably wide authenticated digest, under the approved consensus profile. Here the 64-byte anchor ID refers to one eligible selected-branch header. The proposed eligibility window is the last 64 selected headers. New inputs check current branch spentness even with older eligible anchors; note lifetimes have no expiry. [Ordered tree](relation.py)

O denotes a funded occurrence. A payment creates H(occ,chain,role:u8,sortedNF0,NF1,slot:u8). Sort the two 64-byte NFs lexicographically increasing only for this derivation. Independent public credits derive H(credit_occ,chain,uniqueFundingID64,slot:u8). Distinct paid copies of the same CM can each be spent. Reincluding the same output at another tree index changes the path, while preserving O and its NF. Current-state code must reject repeated occurrences and recreate all branch-local maps on reorg.

## Reference proof relation

The public statement in exact order is chain64 || root64 || count:u48 || fee:u64 || two NFs64 || two CMs64 || intent64 || auth64, 526 bytes. Verifiers reconstruct it from trusted registration/branch and canonical full core. Canonical decoding enforces 1 ≤ count ≤ 2^40, including the full-tree count. Role/backend and the receipts enter intent. Both the proof's own public input binding and the circuit check on auth are required.

The private input record is ASK64 || native8 || asset64 || qty8 || salt64 || O64 || index5 || forty 64-byte siblings, totalling 2,837 bytes. Path arrays start at the leaf. Two such records, two output plaintexts, one byte (0 or 1, active second input) and the common asset ID64 take 6,155 bytes. The Boolean witness has 49,233 bits after omitting the selector's seven fixed zeros. The 64 private O bytes are authenticated through the leaf. Public validators never receive these witness encodings.

1. In each slot derive A from its ASK, open CM on the same note fields and calculate its occupied leaf. Require positive native or qty for both records. Require index < count. Place each node and sibling at their exact left/right positions from the corresponding index bit. The level-39 parent must equal the registered root in each slot.
2. Two real inputs require distinct positions. A single real input requires equal 277-byte scalar records (including ASK, typed opening, O and index); verify both paths. For the first slot and an active second slot compute NF = H(nf,ASK,O). For an inactive second slot use H(dummy_nf,ASK,O). Check each public NF and require they differ. Reserve both in common branch spentness. Include the second input's quantity and native amount in the balance only when active. Secret selection changes the tagged message in one hash call.
3. Across all four notes enforce asset = common ID if qty > 0 else zero. Require common ID nonzero exactly when some qty > 0. Compute both balances in 66 bits. Native inputs = native outputs + public fee; token inputs = token outputs. Maximum native right side is 3(2^64−1). Both zero-valued outputs and native-only outputs have canonical zero ID. The ledger inserts both CMs. A zero output creates no usable money.
4. Derive the two output CMs from their own plaintexts. An output's spending secret belongs to its recipient. Check auth = H(auth,ASK0,intent), with no public descriptor, public receipt salt or payer-known shared secret as the auth key. Old senders knowing their entire chosen note still lack ASK. Repeated identical authorization is deterministic. The joint security of auth and NF under related observations is conditional.
5. The wallet shuffles recipient/change for ordinary payments and permutes two real input slots locally. A one-input transaction has the same public shape. Swap outputs use slot 0 for the counterparty and slot 1 for change. The node admits only genuine registered proofs, checks the current spent set and duplicate economic identities across the whole proposed operation, and appends both occurrences, receipts, nullifiers and a single fee effect atomically.

The tag and selected byte lengths are read back from actual hashlib calls on an honest funded assignment. Keccak chi uses 99 × 24 × 1,600 = 3,801,600 AND gates. Two 40-level paths use 40,960 selector ANDs. The explicit scalar and hash-equality template adds 12,432 ANDs, for 3,854,992 before backend-specific optimizations. XOR/NOT and wire fanout are free in this metric. Byte SHAKE padding and rho/pi routing are public affine wiring. The single Boolean output checks the conjunction. Full adders use 2 ANDs per carry and preserve all 66 bit positions. No known constants are folded in the schedule. This is the cost of an explicit template, separate from a compiled candidate proof or measured prover resources. [Executable gate schedule](side.py)

## Core and receipt wire

The ordered prefix is ASCII FS01 || backend:u8 (1 or 2) || role:u8 (0 ordinary,1/2 ordered swap) || anchorID64 || fee8 || NF0 || NF1 || CM0 || CM1 = 334 bytes. Tails are two 1,792-byte receipts, followed only for a swap leg by terms64 || ephemeralPK64 || expiryHeight8. Intent = H(intent,chain,root,count:u48,prefix,tails); input lengths are 4,054 and 4,190 bytes (30 and 31 permutations). This hash is public. Core = prefix || auth64 || tails || proofLen:u64 || proof. Length must consume the exact remainder. Reject empty proofs, unknown role/backend, unapproved verifier, noncanonical length, bad proof and trailing bytes; proof parameters also bound an actual implementation's allocation. The candidate register and parser determine the whole proof before admitting any transition. One ordinary frame uses 3,990 + P bytes. A signed leg uses 33,918 + P. The whole bundle is FSW1 || firstLen:u64 || secondLen:u64 || signedLeg0 || signedLeg1 = 67,856 + P0 + P1 bytes. The universal `u64` framing is separate from any deployment's maximum permissible packet size.

For each output generate a fresh final ML-KEM-1024 encapsulation to the validated address. Use O derived from final input NFs or independent public credit. Let ad = H(ad,chain,O,slot:u8,CM,kemCT1568) (1,763 input bytes), desc = H(descriptor,chain,A,ek1568) (1,698). HKDF-SHA384 with IKM = ML-KEM secret, salt = desc, info = ad outputs key32 || nonce12. AES-256-GCM authenticates the 208-byte plaintext with ad as AAD, producing 208 ciphertext bytes and a 16-byte tag. Publish kemCT1568 || ciphertext208 || tag16. Distinct contexts and one fresh encapsulation per encryption are required. No external nonce or recipient hint is transmitted. The wallet validates byte widths, supplied chain, supported suite, encapsulation-key checks and authenticated out-of-band address provenance. There is no receipt creation rule that proves a malicious payer handed the recipient usable encryption. An offline wallet must check the GCM tag, exact own A, typed opening and CM before accepting. The native helper checks the authenticated plaintext length, own A and CM; the clear evaluator checks the amount bounds and asset typing. [FIPS 203](https://csrc.nist.gov/pubs/fips/203/final) · [RFC 9935](https://www.rfc-editor.org/rfc/rfc9935.html) · [HKDF](https://www.rfc-editor.org/rfc/rfc5869.html) · [GCM](https://csrc.nist.gov/pubs/sp/800/38/d/final)

The wallet scans the entire authenticated ordered selected-branch transcript for every retained address, rederives occurrences, tests both receipts, tracks current NFs and rebuilds paths locally. At an update or rollback it recomputes affected leaves, snapshots and spentness before spending. A restore requires that same account's original 64-byte backup plus complete authenticated history and the trusted genesis. Retain the outbox input selection over retry. Data completeness, account backup scope and network-level leakage remain explicit. Public headers, proofs and receipt projections have to be independently verified before treating recovered notes as admitted funds.

## Swap and supply

The two independent owners negotiate over a private authenticated channel. For an exact terms encoding, commit H(terms,chain,secretNonce64,PK0,PK1,expiry8,fee0:u64,fee1:u64,receiveDescriptorDigest0,receiveDescriptorDigest1,assetOffered0,nativeOffered0:u64,qtyOffered0:u64,assetOffered1,nativeOffered1:u64,qtyOffered1:u64). All unnamed digest/key/asset widths are 64 bytes; H input is 570 bytes. Require distinct ephemeral public keys and validate each private offered tuple. For leg i, output 0 belongs to the other party. Each side checks both registered cores, actual incoming decrypted note with their own ASK-derived A, asset/native/qty and stipulated fee/split, both keys, common expiry and commitment to its locally agreed salt/terms. Each approves only after the checks. Final message = H(pair,chain,len0:u64,core0,len1:u64,core1); both separate fresh FIPS 205 SLH-DSA-SHAKE-256s keys sign the same 64-byte message under the pure signature mode with empty context. A proof under a swap role is never accepted by itself. Node verifies both signatures (64-byte keys; 29,792-byte signatures), role order, terms/expiry equality, expiry at candidate height, non-repetition across both legs, legal total fee and current eligible anchors. Both independently balanced transfers plus exact approval over both cores atomically settle both offered assets. No public amounts are necessary to check these local bargains. Terms are not publicly opened. One leg may pay zero native fee if the other covers the aggregate policy fee; a signed two-leg fixture allocates 0 and 3. A consensus implementation must credit their exact sum once, with no truncation. [FIPS 205, Table 2](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)

The bounded fresh-genesis supply policy starts with ordered, explicitly trusted public native grants. Zero token, strictly positive native value, and native total < 2^128 are mandatory. Use funding ID H(funding_id,chain,0:u8,grantIndex:u64). The scope tested here has no new native subsidy; fee credit may recycle paid fees at most once. One-time fixed-supply user issuance is permissionless. Pick fresh issuer SLH PK64 and nonce64. aid = H(asset,chain,1:u8,issuerPK,nonce,cap:u64) (203 bytes); reject zero aid, zero cap or duplicate on this branch. Record = FSI1 || issuerPK64 || nonce64 || cap8 || full public note208 || receipt1792 = 2,140 bytes, plus the 29,792-byte issuer signature. Verify pure SLH-DSA-SHAKE-256s over H(issue_body,chain,record) with that PK. Recompute CM and require native=0, qty=cap, note.asset=aid. Install the unique funding ID H(funding_id,chain,1:u8,aid), its slot-zero O, CM and registry cap together. The issuer cannot mint again. Duplicate registrations and failed checks leave this reference prefix unchanged. Supply records are public and reveal the initial public owner and cap. This research prefix charges no issue fee; pricing open registration, ongoing native rewards and managed mint/redemption are additional state policies outside this two-backend comparison. No historical asset inherits a new identity. [Public fixed-supply check](issuer.py)

## Reproduction and limits

With the approved Node 24.22.1 binary on PATH (OpenSSL 3.5.9), from repository root:

```sh
python3 -B experiments/fresh-spend/binding/test_relation.py
python3 -B experiments/fresh-spend/binding/side.py
python3 -B experiments/fresh-spend/binding/lifetime.py
```

Set FS_RECEIPT_NODE to its exact path when another node is first on PATH. All six tests run; a missing provider fails. The offline case starts with 17 synthetic native units, registers 60 fixed tokens with a freshly signed record, rejects duplicate registration, then checks a real two-input/two-output monetary assignment (receiver 8 native/25 tokens; change 6/35; fee 3). Both output envelopes are genuinely sealed, then independently resealed with the same recipients, amounts, commitments, funding, fee and anchor. Both ciphertexts, the intent and auth change while both real NFs repeat. The subsequent receiver spend has disjoint NFs. A fresh native process restores the receiving key from its original backup. The test driver presents the selected public receipt rows to that process and supplies a membership path from the reference tree to the clear evaluator. The change envelope and modified receipt controls miss. The driver does not perform independent full-history discovery or verification. The receiver uses its sole opening in a new one-real-input assignment sending 4 native/20 tokens, keeping 1/5 and paying 3. The two swap assignments use placeholder receipts. A separate signature test signs a pair digest over opaque synthetic cores with two independent real keys. Neither test executes matched swap receipt checks or a jointly proved swap. Further tests check scalar and serialized lengths. Marker bytes in size-only tests are never submitted for proof verification. Histories/paths are built by the clear reference, and no FS01 noninteractive proof, public admission, consensus, p2p replay or swap settlement occurs in these tests.
