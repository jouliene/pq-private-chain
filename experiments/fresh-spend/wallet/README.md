Picnic-L5-UR fixes a LowMC 256-bit block and secret with 38 rounds and ten S-boxes each. The three-party protocol records 1,140 binary AND outputs per view, occupying 143 bytes. Seeds are 32 bytes, commitments are 64 bytes and the proof salt is 32 bytes. Two input shares are seed-derived. The third is chosen to make all three sum to the witness. The prover commits to all three full views and computes a length-preserving `G` image for each. `H3` derives the challenge from all output shares, commitments, `G` images and the public instance and message. Each response opens two adjacent views and reconstructs the first opened AND vector. The wire carries the second opened vector, two seeds, one hidden commitment and the hidden `G` image. The explicit third input share appears inside the hidden image's length when party 2 is hidden or directly as a payload when party 2 is opened. This gives the same wire size in all three cases. [Pinned parameter set](https://github.com/microsoft/Picnic/blob/192cc046744a04d884a99940f92cfe443fda6081/picnic.c#L92-L196) · [Pinned transcript and encoding](https://github.com/microsoft/Picnic/blob/192cc046744a04d884a99940f92cfe443fda6081/picnic_impl.c#L286-L407)

With `t` repetitions, seed width `S`, packed AND vector width `A` and private input width `W`, the optimized encoding with a 64-byte commitment and 32-byte salt has exact size `ceil(2t/8) + 32 + t * (64 + 3S + 2A + W)`. The hidden output share is inferred by XOR against the public result, so a one-bit result adds no wire bytes. The formula gives 209,506 bytes for the source LowMC instance. The component runner checks the same value in the API and on the serialized signatures.

## Applying the geometry to private spending

The fixed relation has two secret depth-40 membership paths, both spending secrets and note openings, output openings, and the hidden second-input activity bit. It binds actual branch-derived root and count, the two real-or-padding nullifiers, both outputs and the same-witness intent authorization. Ordinary and signed legs use the same circuit. The exact AND template is 99 × 38,400 Keccak chi gates plus 40,960 path-routing and 12,432 side gates, totaling **3,854,992**. `A = 481,874` bytes and `W = 6,155` bytes. The complete ordinary nonproof envelope is 3,990 bytes. The signed envelope is 33,918 bytes with terms, expiry, fresh 64-byte approval public key and 29,792-byte SLH-DSA-SHAKE-256s approval. The swap adds 20 bytes to two complete signed legs. The two owners generate their proofs independently from their own witnesses.

One opened-vector trace alone already totals 211,060,812 bytes. The earlier N3B1 used two complete opened views and 560 FS repetitions. The current 560-round UR geometry has almost the same cost, since it replaces one of those big vectors with a hidden image. Its smaller 438-round wire reflects a lower repetition count. Picnic3/Katz–Kolesnikov–Wang preprocessing is a separate protocol with distinct openings and concrete costs. The source `G` appends a little-endian `uint16_t` output length and squeezes exactly that many bytes. Full view images require 481,906 or 488,061 bytes at a 32-byte seed width. Widening the type alone would create a new transcript. A prospective payment encoding would need versioned domain tags, checked wide lengths, exact seed expansion for the private assignment, a canonical fixed public statement, and approved hash/challenge serialization. It would bind the complete unsigned payment and receipts, selected branch anchor, chain and proof suite, role, and complete signed terms or their canonical digest. Verification would reconstruct the first opened view and both opened images from public state and proof bytes, check every first-party AND, match the final relation bit and recompute the challenge. Root/count eligibility, current nullifier insertion, fee booking and the two approvals of a pair remain part of atomic public admission. ## What the security proof addresses

CCS17 Appendix F Theorem 2 and design v2.2 Theorem 5.11 give a simulation-extractability argument for the modified transform under its modeled oracles. The three pair openings have classical special soundness when they are consistent with the same three committed views. XOR of those input shares and the consistency of every gate reconstruct a witness for the evaluated relation. The proof simulator starts by choosing the trits and simulating the two viewed parties, substitutes the hidden commitment and `G` image, and reprograms the challenge. The argument uses hidden-seed entropy, the underlying circuit decomposition simulator, a quantum-secure tape-expansion assumption, and independent idealized oracles. The verifier's recomputation of `G` does not implement the extractor's search over all compatible `G` preimages. The paper does not supply a concrete efficient preimage recovery method for the actual widened SHAKE implementation. The extracted witness would still need to imply funded ledger authorization under the separate commitment, occurrence-binding and spentness games.

Design Lemma 5.9 bounds the nonextractable-yet-accepting challenge event by `2(q_H+1)(2/3)^(t/2)`. At `q_H = 2^128` the logarithms base two for 438, 560 and 660 rounds are +0.8932, −34.7895 and −64.0376. The first term is vacuous at that query budget. At 797 rounds the value reaches −104.1076 before any union of up to `2^40` individual statements, under a separate assumption that each game is covered with the corresponding auxiliary history. These numbers illustrate one term only. Other terms include hash/`G` collision bounds, reprogramming and tape-pseudorandomness errors. The independent ideal-oracle instantiation and the scaling of `q_H` and other query families across a lifetime require their own argument. Treating an entire roughly 636 MB `H3` input as one quantum oracle query also omits time and memory needed to prepare and process that query. The signature-level claim and the hypothetical 64-byte seeds do not yield an end-to-end monetary-security or joint-receipt-privacy guarantee.

The projected joint privacy argument would additionally have to simulate receipts together with proofs on adaptive funded statements, including fake ciphertexts, chosen legitimate recipients, a public chosen-branch history, and independently restored wallets. The spend-intent tag is keyed by the input spending secret and binds the receipts with the rest of the statement. A sender who remembers an output opening knows the plaintext and commitment it created. Linking that opening to an eventual unrelated spend still requires analyzing the state, nullifier, proof, recipient envelope and activity together. Symmetric authentication and threshold cryptographic widths alone do not establish malicious-key anonymity, key robustness or history access-pattern privacy. ## Measurements and modeled workload

A fresh process generated a disposable upstream key and signed three different public messages. Another process, with `HOME` removed from its environment, parsed only the 65-byte public key and the three signatures, accepted all three and rejected a changed message and a changed hidden commitment. The source's KAT executable returned zero. Local sign CPU was 226.2–231.4 ms and public verify CPU was 153.0–154.8 ms. Peaks were 3,628 and 3,400 KiB. A separate first successful run had sign CPU 219.4–223.0 ms and verify 148.8–149.6 ms. These timings reflect the reference LowMC C matrices and bundled SHAKE. Scaling them by the gate ratio would misprice the SHAKE-heavy payment.

Three additional runs measured the prior bit-packed shared Keccak C component and bulk SHAKE256 absorption and squeezing on 482,000-byte data. Prover projection uses a first computation of all three views, both commitment families and the transcript challenge; a second computation regenerates the three views and only the hidden `G` image. The verifier reconstructs two views and two `G` images and hashes the complete challenge input. The specific streaming model interleaves records for challenge absorption. Keeping the stock `H3` order would require an extra image spool, about 635.9 MB written and read per 438-round leg, or another computation pass. Materialization would add about 425 MB per leg or 850 MB per swap before allocator copies. A candidate verifier could reject a declared oversized frame before allocating its payload. At the owner sizing input of 100 million offered operations/year, one illustrative scenario accepts all offers with 90% ordinary and 10% swaps, for 110 million proofs/year. The 438-round packets alone require **46.74 PB/year** per archive or single relay copy, averaging **11.85 Gbit/s** and about **17.4–17.7 cores** for the modeled verification kernels. Twenty years of this workload retains 934.8 PB at one archive before consensus, failures, framing and replicas. The tracked comparison household with 100 Mbps down, 20 Mbps up and two verifier cores would need at least 34.0 seconds to receive one ordinary packet and 170.0 seconds to upload it. Sending one complete pair takes 339.9 seconds at 20 Mbps. These comparison capacities are research assumptions. Every partition that validates full new proofs pays ingest even if it prunes old bodies.

## Offline receiving and upgrade

The 208-byte typed note opening fits an external 1,792-byte receipt with a 1,568-byte ML-KEM ciphertext and a 16-byte GCM tag. Offline recovery needs the originally backed-up high-entropy seed and versioned receive/spend derivation. It authenticates history from its cursor, scans every relevant receipt without disclosing which ones match, opens its own receipt using chain/slot/commitment AD, recomputes the opening's note commitment, reconstructs the occurrence identity from funded history, and obtains a local path to a current eligible root and count. A minimum scan projection of one role byte, two NFs, two commitments and two receipts is 3,841 bytes per leg, **422.51 GB/year** or **8.45 TB in 20 years** in the mixed scenario before authenticated range pages, branch headers and special credits. It entails 4.4 billion decapsulations per retained key over twenty years. The C-era compact-view authentication needs a fresh check here because a tree root over funded commitments and occurrences alone cannot authenticate receipt delivery or completeness. With full body replay, the wallet would instead bear the much larger proof ingest. A real receipt was opened from backup and its onward witness passed the common clear relation. The full authenticated history scan and publicly verified Picnic payment remain unimplemented. [Prior receipt calibration](../../new-note/sha3/CALIBRATION.md) · [Wallet synchronization reference](../../../devnet/WALLET_PROTOCOL.md)

On a fresh genesis there is no legacy import. A later backend with identical note, occurrence and NF meanings can use versioned consensus admission, one shared spent set and fixed candidate-height rules. Moving older funded C notes into these wider notes is a distinct bridge. It needs an authenticated selected legacy anchor and a proof that jointly conserves the exact old and new values, consumes the original NF once and admits only the new outputs. Replaying old blocks and rolling back an activation fork must preserve version, fees, both roots and nullifier state atomically. Recovery for a legacy 32-byte backup can still recover legacy value. Deriving 64 bytes from it does not add fresh entropy to new spend/receipt keys. The existing C-to-N7P2 bridge did exercise old-value consumption and backup-restored onward spending for those exact formats. Its proof and traffic measurements do not apply here. ## Reproduction

Run from the check-out root on Linux with GCC, make, OpenSSL development headers, Python and GNU time. The harness extracts the verified archive into a fresh scratch directory and prints that path. It retains build output, timings and a synthetic public packet. The upstream reference's unmodified GCC flags failed at `mpc_matrix_mul` and `mpc_xor` because their `[3]` array-parameter declarations receive two-element arrays in verification. The implementations loop over the passed party count, which is `2` there. The reproduction keeps those warnings visible with `-Wno-error=stringop-overflow` for the outer library and test only. The SHAKE submake runs separately with its own flags. The earlier combined override also failed because Make propagated the outer warning flags into the SHAKE submake, turning its two unused endianness helper diagnostics into errors. No upstream C code or cryptographic check changes.

```sh
scratch=$(mktemp -d)
curl -fL https://codeload.github.com/microsoft/Picnic/tar.gz/192cc046744a04d884a99940f92cfe443fda6081 \
  -o "$scratch/picnic.tar.gz"
bash experiments/fresh-spend/wallet/reproduce.sh "$scratch/picnic.tar.gz"
python3 -IB experiments/fresh-spend/wallet/price.py | cmp - experiments/fresh-spend/wallet/PRICE.json
```
