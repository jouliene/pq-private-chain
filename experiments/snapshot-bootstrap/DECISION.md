# Continue snapshot bootstrap as an opt-in fast start

Retain genesis replay as the default for a validator that needs fully verified history. The funded C snapshot is worth developing for a returning operator who can obtain an independent registration and wants to validate new payments sooner. In the operator experiment at H39, accepting that temporary trust assumption reduced time to a usable validator from 13.12 to 3.24 seconds. By the time both validators had independently checked history from genesis, the snapshot path had taken 14.94 seconds and downloaded close to twice as many bytes. [Operator measurements](MEASURED.json)

## Same funded tip, two fresh stores

The deployment, source peer, H39 target and two-block suffix were identical. H37 was an ordinary CPU-mined block. H39 contained a freshly proved spend of a pre-base receipt. Bytes below are uncompressed application traffic, including RPC framing, block inventory, work preimages and state transfer. Peak disk is allocated bytes observed in the validator store, including the separate local replay database and SQLite journals. Time includes process and verifier startup.

| Completion point | Elapsed | Requests | Replies | Total traffic | Observed peak disk |
|---|---:|---:|---:|---:|---:|
| Ordinary replay, fully verified | 13.12 s | 3,783 B | 3,711,422 B | 3,715,205 B | 4,161,536 B |
| Snapshot, historical prefix assumed | 3.24 s | 3,934 B | 3,749,093 B | 3,753,027 B | 417,792 B |
| Snapshot, fully verified, cumulative | 14.94 s | 7,529 B | 7,277,078 B | 7,284,607 B | 8,482,816 B |

The canonical state was 37,586 B. The independently obtained registration file was another 460 B delivered outside the download channel. Both paths assumed a preinstalled public runtime (7,557,294 B compressed base distribution). Both fully verified stores finished at 4,083,712 B. Observed peaks by logical file length were 4,158,096 B for ordinary replay, 414,344 B at provisional availability, and 8,480,776 B through full snapshot verification. The measurements come from one small devnet history on a shared host with a warm OS page cache. Raw counts and timing are recorded separately. [Procedure and limits](README.md)

Existing PoW hashes the entire block template, including payment bytes, before hashing with the nonce. The snapshot importer therefore read exactly the same 3,708,923 B of original blocks as the ordinary validator to reach H39. It saved early work by deferring pre-base payment verification. It discarded old templates after checking work. Full corroboration fetched another 3,525,612 B of original bodies, independently verified them and rechecked the locally retained suffix before replacing the database. A compact header download alone could not perform the original work check. The next engineering experiment is a size-bounded local spool for the exact work preimages, comparing eliminated second-download bytes against additional retained and peak disk on a longer, payment-dense branch.

## Receipt and branch evidence

The offline wallet received a single 17-unit native note at H36. The state commits to the hashes of 37 ordered common wallet records; those records total 86,985 B and can be served separately to any wallet. With its funding record unavailable, restoration reported incomplete, exposed no balance and submitted nothing. After service returned, the same 32-byte backup discovered that note. The wallet paid 11, kept 3 change and paid the 3-unit fee. Each complete C payment occupied 182,863 B. Across the failed and resumed wallet scans, the wallet received 80,121 B and 11,759 B of framed history replies respectively. These wallet-side bytes are separate from the validator comparison.

A heavier fork diverged at H36. The losing payment and its fee rolled back; the sender and recipient held 17 and 0 on the winning branch. A fresh restore spent the same old note against the winning anchor, and the two wallets finished with 3 and 11. The two conflicting transactions share the real spent-note nullifier. Only the winning payment charged a fee. The competing branches used the original fork-choice rule. An independently built genesis-only store and the original C implementation matched the selected funds, fee total, registry and spent-set digest. At H41 the selected chain had 4,100 native units issued, 57 cumulative fees, 83 outputs and 42 spent identifiers. The four outstanding asset supplies were 13, 80, 15 and 97. The fast path rejects corrupt state and work data before committing an import. Replacing even one byte of a registered wallet record prevents attachment. Missing original history leaves the live node provisional. A registered history commitment that conflicts with independently replayed state quarantines the database across restart. The fixed public replay also exercises a different outcome: with the original base unavailable, the node can still select a fully validated heavier branch if its own complete ancestry is available. No wallet balance or payment proof is imported from the snapshot provider.

This result concerns startup latency, temporary trust and historical data availability on the funded devnet. It leaves the consensus rules, paid transaction size, and the open end-to-end post-quantum monetary and joint-privacy questions in place. If every source loses a required original, replay through that gap remains impossible with these rules. If every source loses the encrypted receipt and the original carrying it, the seed and snapshot commitments alone cannot restore that receipt.
